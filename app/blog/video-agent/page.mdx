# Designing a Video Agent That Can Actually Make a Long Film

<p className="text-muted-foreground text-sm">November 2026</p>

Honestly, video models are good now. A single clip often passes for footage, and the newest ones film several shots in one go: [Seedance 2.5](https://seed.bytedance.com/en/blog/one-take-creation-flexible-referencing-introducing-seedance-2-5) makes up to 30 seconds in a single generation, and [MiniMax H3](https://minimax.io/blog/minimax-h3) cuts between shots inside one clip.

However, making a whole film is still hard, even a one-minute one. Most people make it shot by shot on an infinite canvas like [Firefly Boards](https://www.adobe.com/products/firefly/features/boards.html), [FLORA](https://www.florafauna.ai/), [TapNow](https://www.tapnow.ai/) or [LibTV](https://www.liblib.tv/), or in research tools like [VideOrigami](https://arxiv.org/abs/2503.04103) that add a script and a scene planner, and then stitch the takes that work together. Some people hand that loop to a coding agent like [Claude Code](https://www.anthropic.com/product/claude-code), or to the agents these tools now have.

What comes out tends to play like a **slideshow**.

Try making a one-minute film with Claude Code and a video model, and you'll see what I mean. Each shot looks fine on its own but doesn't belong with the one before it. Clips start from a still and stop before the cut, motion and sound don't carry across, and no one planned the rhythm: which moment gets a close-up, which holds, where to cut. Consistency slips too: an old woman's face, or the scarf she knits, changes from shot to shot.

The clips aren't the problem. Today's video agents weren't built for long videos, and their harnesses leave the problems specific to film unsolved: how to plan a scene's shots, what the agent needs to know about film to pace them and write the storyboard, how to keep people, places and looks consistent and the motion continuous across cuts, and how to let the story flow from one scene to the next.

I've been working on these problems in [Doki Agent](https://doki.mov) (Doki's interface is also super interesting, but I'll save it for another post). This post is about the four parts that did most of the work of turning many clips into one film, which I think any video agent needs, however it's built:

1. **Definition System**: what has to look the same, and how each generation is told.
2. **Shot Planning**: how a scene is split into generations for the best continuity.
3. **Incremental Editing**: how a change reaches the film without re-rolling it.
4. **Review Loop**: how the agent checks what it made and improves it on its own.

Everything below comes from building Doki: the real prompts, what broke, and what fixed it.

## 1. Definition System

A long film shows the same people, places, objects and looks across dozens of generations, and image and video models remember nothing from one generation to the next. Each one sees only its own prompt and a few reference images, so anything that exists only as words is drawn anew every time. A video agent therefore needs a **definition system**: everything the film reuses is defined once, with a description and a reference image, and every shot references it instead of describing it again. Before each generation, the agent resolves the shot's references into the definitions and images the model needs.

### Definitions

A definition needs four parts: a type (a character, a place, an object, a look), a name the script can reference, a description, and a reference image made from that description. Two from _The Last Three_, an example film made in Doki:

Every shot that references <T>@Camera</T> is generated with that image, so the tape that reads "3 left" looks the same in all of them. The image does most of the work; the description is what the image is made from, and what each prompt repeats.

### Resolving a shot

Definitions use other definitions: a photo of Mio on the platform needs both Mio and the platform. So the references form a dependency graph, and resolving a shot means walking it. Here is one shot of _The Last Three_, in which a girl named Mio leaves her last three photos at a shop:

<ResolveFigure />

Walk the graph depth-first from everything the shot references (its own tags, plus whatever applies to the whole film or its section), and emit each definition after the ones it uses:

```ts
const resolve = (tag: Tag) => {
  if (seen.has(tag)) return // each once, so cycles stop
  seen.add(tag)
  tagsIn(tag.definition).forEach(resolve)
  ordered.push(tag) // after everything it uses
}
;[...shot.tags, ...globals, ...fromHeadings].forEach(resolve)
```

The order matters because the prompt lists the definitions in it: by the time the model reads that <T>@WindowPhoto</T> is "<T>@Mio</T> on a train", it already knows who Mio is. Keep the graph, too. Read backwards, it tells you what a change breaks: change Mio, and every shot that reaches her, directly or through a photo of her, is out of date (section 3).

### Choosing the reference images

A shot can reach more definitions than a model takes images, which is four to six for video models right now, so the agent has to choose. Two rules worked:

- **The scene so far.** Send the scene's earlier shots with every new image, so the scene keeps its place, light and people. This was the biggest consistency win I measured: it cut errors by more than half.
- **What the first frame doesn't show.** A video starts on its first frame, which already shows whoever is on screen. Spend the slots on the rest: the person about to walk in, the place a cut moves to.

Label each image with what the model should take from it. An unlabeled style reference gets its subject matter copied into the shot:

<Prompt from="Doki's image prompt writer">
  An image that is "the overall style" [...] gives only that quality ("in the
  art style of image 3"). Never put its content in the shot.
</Prompt>

### What gets a definition

Anything seen more than once that should look the same, however small. Don't leave that to the agent's judgment. An earlier version of my prompt said "characters and key places or objects" get a reference image, and the agent decided that a coin, a takeout bag and an orange were simple enough to describe in words, and that a scarf an old woman knits on a train, which a girl wears at the end, "changes form". All of them came out different in every shot. What fixed it was explaining how the models behave instead of naming a category:

<Prompt from="Doki's agent prompt">
  Without one, they get only its text, and each picture draws it anew - each
  shot's image, and each later cut, which has no image of its own: the same
  words come out as a different face, outfit, place or object each time, however
  small or plain it is. [...] So whatever is seen more than once and should look
  the same each time - someone, a place, a vehicle, a prop - gets a definition
  with a reference shot.
</Prompt>

After that change, the scarf got its own definition every time, and continuity errors in my storyboard tests fell by about a fifth.

A reference image also holds everything it shows. If a shop's reference shows it from the street, every shot that uses it pulls toward the street, even the ones set inside. So a place's interior, a costume from another decade, or what a character turns into each needs a definition of its own.

### Words beat pictures

When the prompt and a reference image disagree, image models follow the prompt. Give a character yellow boots in the text, and the red ones in her reference vanish. Models also sometimes skip the images and draw from the text alone: a grandmother the prompt named only by her cardigan came out as a stranger in a cardigan. So the prompt should add no looks to anything that has a reference, and describe each person by who they are (age, face, hair, build) before their clothes.

The same goes for the cuts inside a clip, which a model filming several shots at once draws fresh: in half of my test clips, a black-and-white noir turned to color right after the first cut. One sentence in the video prompt fixed it:

<Prompt from="Doki's video prompt writer">
  The video model draws each later shot afresh and drifts from the film's look
  unless told it, so open each shot after the first with the look in a few words
  [...] ("cuts to a close-up, in the same high-contrast black and white: …").
</Prompt>

**If you're building one**

- Give everything that appears more than once and should look the same a definition with a reference image. Don't leave it to the agent to judge what's important.
- Resolve definitions depth-first and list them in dependency order. Keep the graph, since you'll need it in reverse.
- Spend the image budget on the scene so far and on what the first frame doesn't show, and label every image with what to take from it.
- Never add visual details in words to a defined thing. Restate the style at every cut.

## 2. Shot Planning

The slideshow look comes from the obvious pipeline: one storyboard image and one clip per shot, cut together. Each clip starts from a still, its motion and sound start from zero, and left alone it slows to a stop before its cut. A video agent needs a planner instead, one that decides which shots are filmed together in one generation, where a long scene splits into clips, and how each clip's prompt keeps the motion going through its cuts.

### Film the scene, not the shot

Newer video models can film several shots in one generation and cut between them. Inside one generation, people, light, motion and sound carry across the cuts, and a reverse angle can show the other side of the room, which separate images struggle with (image models tend to copy the earlier shot's camera position). So the unit of generation should be the scene. In my tests, a scene made as one clip beat the same shots made separately in most pairwise comparisons, with about a third fewer continuity breaks.

### Where to split

One clip isn't free, and a scene can run longer than a generation (10 to 30 seconds right now). Inside a clip, only the first shot opens exactly on its storyboard frame; the later ones open close to theirs. A clip boundary resets the motion and the sound instead. Which costs more depends on the cut and the shot: a line of dialogue and its reply shouldn't be split, while a reveal or a product shot needs its exact frame.

So before filming a scene, have a model read its shots (the text and the storyboard frames) and rate two things from 0 to 3: for each cut, how much the two sides need to be one take, and for each shot, how much it needs its exact frame. Two lines of the cut rubric:

### Writing the clip

A clip's prompt has to give the model something to play, keep it moving, and say it in the model's own terms.

**Open on the first instant.** About 40% of our first frames showed a moment later than the start of the shot. "She walks to the porch, crouches and watches the kitten" produced an image of her already crouched, leaving the clip nothing to play. Image models draw any action the prompt names as already done, so describe the frame as a still photograph, and have the prompt writer start with the opening moment on its own line (`OPENING: she reaches the porch steps`), which forces it to pick a single instant:

<Prompt from="Doki's image prompt writer">
  The image model draws whatever the prompt names as done: an action's verb,
  even with "starting to" or "about to", comes out finished ("starting to sit"
  comes out seated) [...] So write the prompt as a still photograph of that
  instant, in states rather than actions: where each person is, where their
  hands, gaze and weight are, and where each object is.
</Prompt>

**Keep moving through the cut.** The other end of the clip needs the same care. Tell the video prompt writer what a stop does to the film:

<Prompt from="Doki's video prompt writer">
  A clip that slows to a stop before its cut makes the film halt there, and when
  every clip does, the film plays like a row of stills. So unless NEXT SHOT is
  none, keep the action and the camera moving through the last second [...]
</Prompt>

**Speak each model's dialect.** MiniMax ignored timed spans like `[2-4s] cut to …` and often cut at around two seconds whatever we wrote. Written in its own shot-list syntax, it cut within a few hundredths of a second of our timestamps:

### What I got wrong

**Count the plans.** For another video model, the calibrated numbers said later shots drift a lot from their storyboard frames, so the planner split scenes much more, giving about half of all shots a clip of their own. Blind comparisons rated these films no better or worse than the fewest-clips plans. Then I watched one myself and saw shots ticking by at 5 seconds, 5 seconds, 5 seconds, just like the old one-clip-per-shot slideshow, and we went back to the fewest clips for that model. An optimum people can't see the reason for looks like a regression, so count what your planner does before you ship it.

**Keep generation limits out of the story.** When the writing agent was told that a scene becomes "one clip, of up to 15s", it stopped writing scenes longer than 15 seconds and split scenes set in one place to fit. A parameter of the planner had leaked into the screenwriting. Once it was told how scenes become clips without the number, its scenes went back to the length the story called for, and the planner handled the splits.

**If you're building one**

- Generate a scene's shots together when the model can, using the model's native shot-list syntax.
- Plan clip boundaries as an optimization over cuts and frames, with losses calibrated per model.
- Make each frame the opening instant, written in states. Keep clips moving through their cuts.
- Hide model duration limits from the writing agent, and count the plans before shipping a planner.

## 3. Incremental Editing

A long film is never right on the first try, and it keeps changing as you work: a character's hair, a planet that should be frozen, a new line of dialogue. Regenerating whatever a change touches is the default, and it's a coin flip. In my logs, when a review flagged a problem and the shot was made again, the remake fixed it about half the time, and a second try did no better than the first. Each remake also throws away what was right: the camera angle, the faces, the take the user approved.

A video agent should treat the film like a build instead: know exactly what is out of date, and rebuild as little as possible, editing wherever it can. Models can edit now. Give one an image or a clip and an instruction, and it changes what you asked and keeps the rest ([Gemini Omni](https://ai.google.dev/gemini-api/docs/omni) is the one I use for video).

### Staleness is a diff

For every image and clip, record what it was made from: the shot's text, the resolved definitions, the versions of the reference images and, for a video, the frame it starts on, its timing and the clip it shares. Staleness is then a diff between that record and the film as it is now, and it comes with reasons ("<T>@Mars</T> changed"). Because definitions resolve through the graph from section 1, a change reaches every shot that depends on it, directly or not. Write the record only after a generation succeeds, so a failed run never marks a shot up to date.

### Keep, edit or remake

For each stale image and video, have a fast model compare what it was made from with what the shot says now, and pick one of three:

<UpdateFigure />

Most of the judge's prompt describes what an edit can and can't do:

<Prompt from="Doki's update judge">
  An edit does a change that sits in the picture: a color, clothes, hair or
  makeup, an object added, removed or swapped, the state an object is in, an
  expression, the light, the weather or the time of day, written text, the
  style. [...] It can't move the camera or change the framing, move people,
  change what they do or how they move, or set the shot somewhere else; in a
  video it can't change what is said, the voices or the timing.
</Prompt>

The edit model sees the pixels but not the script, so the judge should write its instruction in visual terms ("the woman in the red coat"), never in tags. On 62 labeled cases, Doki's judge chose right 61 times. Put guardrails around it in code: a failed edit falls back to a remake, a shot gets at most three edits in a row, a new image always means a new video, and a photo the user uploaded is never drawn over.

Send video edits to whichever model does them best. Omni kept the motion frame for frame; another model we tried performed the motion again with the change, close but not the same take. So every video edit in Doki goes to Omni, whatever model made the clip.

### Remake the smallest run

When a scene shares one clip, changing one shot shouldn't reshoot the scene. If the change can be an edit, cut that shot's part out of the clip, edit it, and keep the result as the shot's own video. If it needs a remake, make only the run of consecutive shots that need new video, and leave the others alone. The cost is a clip boundary where there wasn't one.

The cheapest fix of all is a trim. Cutting the half second where a hand warps costs nothing, so give the agent a trim tool and tell it to fix a shared clip in order of cost: a trim first, then words an edit can follow, and only then the clip again. Keep every version, so a remake that came out worse can be put back.

**If you're building one**

- Record the exact inputs for every generated asset. Staleness is a diff against those inputs, with reasons.
- Triage stale outputs into keep, edit or remake by clearly specifying what an edit model can and can't change.
- Write edit instructions using visible descriptions, never internal tags.
- Prefer a trim to an edit and an edit to a remake, regenerate only the smallest contiguous run, and version everything.

## 4. Review Loop

A video agent can't fix what it doesn't see, and even a multimodal one rarely sees the film it's making. It writes each shot long before that shot exists, it doesn't look at what comes back unless something makes it, and many models still can't watch a video with its sound (in Doki, Gemini does the watching for the agent). Yet almost everything above pays off on screen. So the agent needs a feedback loop built into its harness: reviews that run at fixed points as it works, whose findings come back inside its tool results.

### Reviews the harness runs

Don't count on the agent to look on its own. I gave Doki's agent a tool to inspect any shot, which has a vision model watch it and answer questions, and across sixteen writing runs the agent called it on its own zero times. So the reviews run in the harness, the code around the agent that executes its tools:

In storyboard tests, films made with these reviews won most blind comparisons against films made without them, with about a fifth fewer continuity breaks.

### The first-time viewer

My favorite check is the first-time viewer: a model that watches the finished film with no script and no request, and says what it understood. The film review has read the script, so it fills in what the pictures leave out. The viewer can't, so wherever their account differs from the script, the film isn't telling the story.

<Prompt from="Doki's first-time viewer">
  Say what you understood, in plain words: [...] What you couldn't follow: who
  someone is or is to someone else, why something happens, where things are,
  what something means, what comes out of nowhere, what you expected that never
  came - each with its shot.
</Prompt>

### What makes reviews work

- **Watch clips, not frames.** Findings from watching whole clips with their sound were real nearly every time, while findings from three sampled frames per clip held up about two times in three. Only whole clips caught a bicycle rolling backward, a hand that never lets go of a cup, or a voice that changed between shots.
- **Tell a gap from a hedge.** The viewer would write that a film "never confirms the boy is him", and the review would ask for a fix, though asked directly, the viewer named the boy right every time. One sentence telling the review that a viewer who understood but hedged has understood removed the false alarms and kept the real catches.
- **Fixes fit the film.** Left alone, the agent answered story critiques by adding beats: a 20-second chase went from 9 beats to 17, and the clips broke more often. Tell every review that a fix "has to fit in the shots the film has [...] and never add a shot, a part or a cut."
- **A refused look is a failure.** When a vision model's safety filter refused a harmless script about a ten-year-old girl, the empty answer read as "no problems found". A refusal should tell the agent the shot went unchecked.
- **Cap the loop.** Review each shot at most three times a request. Before the cap, one run made 24 images chasing its own reviews.

Checking the script instead of the pictures doesn't work. A text-only continuity checker flagged plenty in the scripts and changed nothing in the films, because most continuity errors happen in generation: a cut inside a clip that forgets where someone was standing, a prop that morphs. Only looking at the output catches those.

### What the agent is told

The reviews show the agent its work after the fact. Its prompt has to cover the rest: the habits whose payoff it can't see while it writes. In general, agent prompts should say what exists and what it costs, not what to do. Rules get applied mechanically: a rule to "fade in and out of the whole video" faded a tense dialogue scene in and out too. Examples get copied: one sample scene that opened wide and cut close made the agent open twice as many scenes that way. Facts alone worked for most things, but not for consistency. Told only what a reference image does and costs, the agent made almost none. A comment at the top of Doki's agent prompt records why it makes an exception:

<Prompt from="Doki's agent prompt, its opening comment">
  [...] the habits whose payoff shows only in images and videos it never sees:
  the three that keep a film consistent (a scene in one paragraph, reference
  shots, an ALL for the shared look) [...] Told only what those do, the agent
  left them out: its films were rows of long single takes.
</Prompt>

When the agent can't see a habit's payoff, state the habit outright or enforce it in code. And keep numbers out of the prompt: a number reads as a target, as the 15-second clip limit did.

### Evaluating the agent itself

The same rule applies to whoever builds the agent: judge the film, not the text. A prompt change that won 15 to 6 when a judge read the prompts tied 3 to 4 on the clips they produced. The only evaluation I trust now is watching finished films, blind and in both orders, and counting a win only when both orders agree. Run identical code against itself to see the noise, which across eight films is large. Rerun the baseline on the same day as the experiment, since hosted models drift. And to test one decision, replay saved runs up to that point instead of regenerating whole films.

**If you're building one**

- Trigger reviews from the harness, and return what they find inside tool results.
- Review whole clips with their sound, review the assembled film, and add a viewer who hasn't seen the script.
- Treat a refusal as a failed check, cap the review loop, and keep fixes within the shots you have.
- State the habits whose payoff the agent can't see. Everywhere else, give it facts rather than rules, examples or numbers.
- Evaluate your changes on finished films, never on prompts.

## Last thing

None of these ideas is tied to Doki's script format. Whether you're building a chat agent driving a video API, a node-based canvas or a timeline editor, making a film means coordinating dozens of separate generations, so the agent needs a definition system, a shot planner, incremental edits and a review loop. Video models will absorb parts of this as clips get longer, reference slots multiply and editing improves. What I don't expect to change is that a film is many generations, and that the agent writing it won't watch it unless you make it.

I'm still figuring plenty of this out. If you're building a video agent too, I'd love to hear what's worked for you.
