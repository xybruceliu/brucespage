# Designing a Video Agent That Can Actually Make a Long Film

<p className="text-muted-foreground text-sm">November 2026</p>

Honestly, video models are good now. A single clip often passes for footage, and the newest ones film several shots in one go: [Seedance 2.5](https://seed.bytedance.com/en/blog/one-take-creation-flexible-referencing-introducing-seedance-2-5) makes up to 30 seconds in a single generation, and [MiniMax H3](https://minimax.io/blog/minimax-h3) cuts between shots inside one clip.

However, making a whole film is still hard, even a one-minute one. Most people make it shot by shot on an infinite canvas like [Firefly Boards](https://www.adobe.com/products/firefly/features/boards.html), [FLORA](https://www.florafauna.ai/), [TapNow](https://www.tapnow.ai/) or [LibTV](https://www.liblib.tv/), or in research tools like [VideOrigami](https://arxiv.org/abs/2503.04103) that add a script and a scene planner, and then stitch the takes that work together. Some people hand that loop to a coding agent like [Claude Code](https://www.anthropic.com/product/claude-code), or to the agents these tools now have.

What comes out tends to play like a **slideshow**.

Try making a one-minute film with Claude Code and a video model, and you'll see what I mean. Each shot looks fine on its own, but it doesn't belong to the one before it. Every clip starts from a still and eases to a stop before its cut, the motion and the sound don't carry across, and the shots have no rhythm: nobody decided which moment gets a close-up, which one holds, or where a cut should fall. Consistency slips too, so an old woman's face, or the scarf she knits, changes from shot to shot.

The clips aren't the problem. Today's video agents weren't built for long videos, and their harnesses leave the problems specific to film unsolved: how to plan a scene's shots, what the agent needs to know about film to pace them and write the storyboard, how to keep people, places and looks consistent and the motion continuous across cuts, and how to let the story flow from one scene to the next.

I've been working on these problems in [Doki](https://doki.mov), a video editor where you write a film as a script and an agent writes and makes it with you. Doki's interface is its own thing, and I won't cover it here. This post is about the four parts that did most of the work of turning many clips into one film, which I think any video agent needs, however it's built:

1. **Memory**: what has to look the same, and how each generation is told.
2. **Planning**: how a scene is split into generations.
3. **Editing**: how a change reaches the film without re-rolling it.
4. **Feedback**: how an agent that only reads text finds out what it made.

Everything below comes from building Doki: the real prompts, what broke, and what fixed it.

## 1. Memory

Image and video models remember nothing. Each shot's image and each video clip are generated solely from their own prompt and the images passed alongside it. If a character exists only as words, every generation draws a new person who fits those words. Even inside a single clip, when the model cuts to a close-up, it draws that close-up from scratch.

Most models do accept a few reference images alongside the prompt, and they draw what's in them. That's the only memory you get. So the first thing a video agent needs is a list of everything the film reuses (the people, places, objects and looks), each with a name, a description and a reference image that goes into every generation using it. In Doki each item is a line in the script, and the <span className="mx-0.5">🎬</span> makes its image:

Every shot that tags <T>@Camera</T> is drawn from that image, so the tape reading "3 left" looks the same in all of them.

**Don't let the agent decide what's important.** An earlier version of my prompt said "characters and key places or objects" get a reference image, leaving the agent to decide what counted as key. It decided a coin, a takeout bag and an orange were simple enough to describe in words. A scarf an old woman knits on a train, which a girl wears at the end, "changes form", so it got no image either. All of them came out different in every shot. What fixed this was explaining how the models actually behave, instead of handing the agent a category:

<Prompt from="Doki's agent prompt">
  Without one, they get only its text, and each picture draws it anew - each
  shot's image, and each later cut, which has no image of its own: the same
  words come out as a different face, outfit, place or object each time, however
  small or plain it is. [...] So whatever is seen more than once and should look
  the same each time - someone, a place, a vehicle, a prop - gets a definition
  with a reference shot.
</Prompt>

After that change, the scarf got its own entry every time, and continuity errors in my storyboard tests dropped by about a fifth.

One more catch: a reference image carries everything in it. If a shop's reference shows it from the street, every shot tagged with it pulls toward the street, even the ones set inside. So the interior of a place, a costume from another decade or what a character transforms into each needs its own entry and image.

**Resolve entries in dependency order.** Entries can refer to other entries. Here's one shot from _The Last Three_, one of Doki's example films, where a girl named Mio leaves her last three photos at a shop.

<ResolveFigure />

Resolving a shot is a depth-first walk over everything it uses (its own tags, the film-wide look, and whatever its section heading adds), emitting each entry after its dependencies:

```ts
const resolve = (tag: Tag) => {
  if (seen.has(tag)) return // each once, so cycles stop
  seen.add(tag)
  tagsIn(tag.definition).forEach(resolve)
  ordered.push(tag) // after everything it uses
}
;[...shot.tags, ...globals, ...fromHeadings].forEach(resolve)
```

Order matters because the prompt lists the definitions in that order: by the time the model reads that <T>@WindowPhoto</T> is "<T>@Mio</T> on a train", it already knows who Mio is. Keep this graph around, too, because reading it backwards tells you what an edit breaks. Change Mio, and every shot that reaches her, directly or through a photo of her, is out of date (more on this in section 3).

**Spend the image budget carefully.** Video models accept only a handful of reference images, four or six right now, and a shot can easily reference more entries than that. Two rules decide what makes the cut. First, the scene's earlier shots go into every new image generation, so the scene keeps its place, light and people; this was the biggest consistency win I measured, cutting errors by more than half. Second, for video generation, the opening frame already shows whoever is on screen, so reference slots go first to what that frame doesn't show: the person about to walk in, or the place a cut moves to.

Label every reference image with what the model should take from it. An unlabeled style reference will have its actual subject matter copied into the shot:

<Prompt from="Doki's image prompt writer">
  An image that is "the overall style" [...] gives only that quality ("in the
  art style of image 3"). Never put its content in the shot.
</Prompt>

**Words beat pictures.** Image models trust the prompt's text over the reference image. When our prompt writer gave a character yellow boots in the text, the red ones in her reference vanished. Models also occasionally ignore the images and draw from text alone: a grandmother whom the prompt named only by her cardigan came out as a stranger in a cardigan. Never add visual details in text to an item that already has a reference, and describe each person by who they are (age, face, hair, build) before mentioning their clothes.

The same applies to cuts within a single clip. A model filming several shots at once draws each subsequent shot fresh; in half of my test clips, a black-and-white noir turned to color right after the first cut. One sentence fixed it:

<Prompt from="Doki's video prompt writer">
  The video model draws each later shot afresh and drifts from the film's look
  unless told it, so open each shot after the first with the look in a few words
  [...] ("cuts to a close-up, in the same high-contrast black and white: …").
</Prompt>

**If you're building one**

- Anything seen twice that should look the same gets a reference image. Don't leave it to the agent to judge what's important.
- Resolve entries depth-first and list them in dependency order. Keep the graph, since you'll need it in reverse.
- Spend the image budget on the scene so far and on what the first frame doesn't show, and label every image with what to take from it.
- Never add visual details in words to a defined thing. Restate the style at every cut.

## 2. Planning

Most video agents, Doki included, work in two steps: first generating a still image for each shot (a storyboard frame that's cheap to check and redo), then generating a video clip starting from that image. The obvious pipeline makes one image and one clip per shot and cuts them together. Because each clip starts from a still, its motion and sound start from zero, and left to itself it slows down near the end. Early on, Doki's films looked to me like a beginner splicing clips: a row of slides.

**The image is the opening instant.** About 40% of our first frames showed a moment later than the start of the shot. "She walks to the porch, crouches and watches the kitten" produced an image of her already crouched, leaving the video clip nothing left to play. Image models draw any action the prompt names as already done. Now, our prompt writer describes the frame as a still photograph, and its output must start with the opening moment on its own line (`OPENING: she reaches the porch steps`), forcing it to pick a single instant:

<Prompt from="Doki's image prompt writer">
  The image model draws whatever the prompt names as done: an action's verb,
  even with "starting to" or "about to", comes out finished ("starting to sit"
  comes out seated) [...] So write the prompt as a still photograph of that
  instant, in states rather than actions: where each person is, where their
  hands, gaze and weight are, and where each object is.
</Prompt>

**Keep moving through the cut.** The tail end of the clip needs the same care. We tell the video prompt writer what happens to the film when a clip comes to a stop:

<Prompt from="Doki's video prompt writer">
  A clip that slows to a stop before its cut makes the film halt there, and when
  every clip does, the film plays like a row of stills. So unless NEXT SHOT is
  none, keep the action and the camera moving through the last second [...]
</Prompt>

**Film the scene, not the shot.** Newer models can film several shots in one generation and cut between them. People, light, motion and sound carry across those cuts, and a reverse angle can show the other side of the room, which separate images struggle with (image models tend to copy the earlier shot's camera position). So Doki films a scene's shots together whenever the model supports it. In my tests, generating a scene as one clip beat generating the same shots separately in most pairwise comparisons, with about a third fewer continuity breaks.

**Speak each model's dialect.** MiniMax ignored timed spans like `[2-4s] cut to …` and often cut at around two seconds regardless of what we wrote. Formatted in its native shot-list syntax, though, it cut within a few hundredths of a second of our timestamps:

**Where to split.** A scene can run longer than one generation can hold (10 to 30 seconds right now), and even when it fits, packing everything into one clip has a tradeoff. Only a clip's first shot opens on its exact storyboard frame; subsequent shots inside that clip open merely close to theirs. A clip boundary, on the other hand, resets the motion and sound. Which penalty hurts more depends on the cut and the shot. A line of dialogue and its reply shouldn't be split across clips, whereas a reveal or a product shot needs to hit its exact storyboard frame.

Before filming a scene, a model reads its shots (both the text and the storyboard frames) and scores two things from 0 to 3: for each cut, how badly the two sides need to stay in one take; and for each shot, how badly it needs its exact frame. Here are two lines from the cut rubric:

**Count the plans.** For another video model, our calibrated numbers showed that later shots drifted heavily from their storyboard frames, so the planner split scenes much more aggressively, giving about half of all shots their own clip. Blind evaluations rated these films no better or worse than simple fewest-clips plans. Then I watched one myself and saw shots ticking by at 5 seconds, 5 seconds, 5 seconds, looking just like the old one-clip-per-shot slideshow. We went back to fewest-clips for that model. An optimum people can't see the reason for looks like a regression, so count what your planner does before you ship it.

**Keep generation limits out of the story.** When our writing agent was told that a scene becomes "one clip, of up to 15s", it stopped writing scenes longer than 15 seconds and split single-location scenes to fit. A parameter from the planner had leaked into the screenwriting. Once we explained how scenes become clips while omitting the 15-second number, its scenes returned to the natural length the story called for, and the planner handled the splits.

**If you're building one**

- Make each frame the opening instant, written in states. Keep clips moving through their cuts.
- Generate a scene's shots together when the model can, using the model's native shot-list syntax.
- Plan clip boundaries as an optimization over cuts and frames, with losses calibrated per model.
- Hide model duration limits from the writing agent, and count the plans before shipping a planner.

## 3. Editing

A five-minute film has dozens of clips, and many will come out wrong on the first try. The film also evolves as you work: you change a character's hair, freeze a planet, or add a line of dialogue. The naive response is to regenerate. In our logs, when a review flagged a problem and we regenerated the shot, the remake fixed it only about half the time, and a second try did no better than the first. Re-rolling is a coin flip that throws away everything the previous take got right: the camera angle, the faces, the take the user approved.

Fortunately, models can edit media directly now. Give one an image or clip and an instruction, and it changes what you asked while keeping the rest ([Gemini Omni](https://ai.google.dev/gemini-api/docs/omni) is what I use for video). Treat the film like a software build: track exactly what is out of date, and rebuild as little as possible.

**Record what each output was made from.** Whenever Doki generates an image or video, it logs the exact inputs: the shot's text, the resolved definitions, the versions of the reference images, and (for video) the starting frame, timing and shared clip. Staleness is simply a diff between that saved record and the film as it is now, complete with human-readable reasons ("<T>@Mars</T> changed"). We write the record only after a generation succeeds, so a failed run never marks a shot as up to date.

**Keep, edit or remake.** For every stale image or video, a fast model compares what the shot was originally built from against what the script says now, choosing one of three actions.

<UpdateFigure />

The judge's prompt mostly defines the boundaries of what an edit model can and cannot pull off:

<Prompt from="Doki's update judge">
  An edit does a change that sits in the picture: a color, clothes, hair or
  makeup, an object added, removed or swapped, the state an object is in, an
  expression, the light, the weather or the time of day, written text, the
  style. [...] It can't move the camera or change the framing, move people,
  change what they do or how they move, or set the shot somewhere else; in a
  video it can't change what is said, the voices or the timing.
</Prompt>

Because the editing model sees the pixels without the script, the judge writes its instructions purely in visual terms ("the woman in the red coat"), never using script tags. Across 62 labeled test cases, this judge picked the right action 61 times. A few hard guardrails wrap around it in code: a failed edit falls back to a remake, a shot can be edited at most three times in a row, a new image always triggers a new video, and user-uploaded photos are never drawn over.

Route video edits to whichever model handles them best. Omni preserved the original motion frame for frame. Another model we tested performed the motion again with the requested change, which looked close, though it lost the original take. Every video edit in Doki goes to Omni, regardless of which model generated the source clip.

**Remake the smallest run.** When a whole scene lives in one shared clip, changing a single shot shouldn't force a reshoot of the entire scene. If the change qualifies for an edit, Doki slices that shot's segment out of the shared clip, runs the edit, and stores the result as that shot's standalone video. If it requires a full remake, Doki regenerates only the contiguous run of shots needing new video, leaving the surrounding shots untouched. The only cost is introducing a clip boundary where there wasn't one before.

The cheapest fix of all is a trim. Snipping out the half second where a hand warps is free, so the agent has a trim tool and instructions to repair shared clips in strict order of cost: try a trim first, then rewrite for a visual edit, and regenerate the clip only as a last resort. Doki keeps every historical version, so if a remake comes out worse, you can always revert.

**If you're building one**

- Record the exact inputs for every generated asset. Staleness is a diff against those inputs, with reasons.
- Triage stale outputs into keep, edit or remake by clearly specifying what an edit model can and can't change.
- Write edit instructions using visible descriptions, never internal tags.
- Prefer a trim to an edit and an edit to a remake, regenerate only the smallest contiguous run, and version everything.

## 4. Feedback

The agent orchestrating all of this is a language model. It lives entirely in text, while almost everything discussed above pays off in pixels it never sees. That blindness has two consequences.

**Tell it the habits whose payoff it can't see.** In general, I prefer agent prompts that state what exists and what it costs, rather than prescribing rules. Explicit rules get applied mechanically: a rule to "fade in and out of the whole video" faded a tense dialogue scene in and out too. Examples get mimicked blindly: including one sample scene that opened wide and cut close caused the agent to open twice as many scenes that exact way. Giving facts alone worked well for most tasks, except visual consistency. Told only what a reference image does and costs, the agent created almost none. A comment at the top of Doki's agent prompt records why we made an exception:

<Prompt from="Doki's agent prompt, its opening comment">
  [...] the habits whose payoff shows only in images and videos it never sees:
  the three that keep a film consistent (a scene in one paragraph, reference
  shots, an ALL for the shared look) [...] Told only what those do, the agent
  left them out: its films were rows of long single takes.
</Prompt>

Whenever the agent can't observe the downstream payoff, either state the habit outright or enforce it in code. And keep arbitrary numbers out of the prompt: a number reads as a target, as the 15-second clip limit did.

**Show it what it made.** We gave the agent a tool to inspect any shot (calling a vision model to watch and answer questions). Across sixteen writing runs, the agent called that tool on its own zero times. So we moved reviews into the harness, the wrapper code executing the agent's tools, and injected the review findings directly into tool results where the agent can't ignore them.

<ReviewFigure />

In storyboard tests, films built with these automated reviews won most blind comparisons against films built without them, with about a fifth fewer continuity breaks.

My favorite check is the first-time viewer. Because the main film reviewer has read the script, it fills in narrative gaps that the visuals leave out. A fresh viewer with no script can't cheat, so anywhere their summary diverges from the script, the film itself is failing to tell the story.

<Prompt from="Doki's first-time viewer">
  Say what you understood, in plain words: [...] What you couldn't follow: who
  someone is or is to someone else, why something happens, where things are,
  what something means, what comes out of nowhere, what you expected that never
  came - each with its shot.
</Prompt>

A few practical details determined whether these reviews actually improved the film or just burned tokens:

- **Watch clips, not frames.** Findings from watching full clips with their audio were real nearly every time, whereas findings from three sampled frames per clip held up only about two times in three. Only full clips caught a bicycle rolling backward, a hand that never lets go of a cup, or a voice that changed between shots.
- **Tell a gap from a hedge.** The viewer would write things like "the film never confirms the boy is him", prompting the reviewer to demand a fix, even though when asked directly, the viewer named the boy right every time. Adding one sentence telling the reviewer that a viewer who understood while hedging has still understood eliminated the false alarms while keeping the real catches.
- **Fixes fit the film.** Left unconstrained, the agent responded to story critiques by cramming in extra action beats: one 20-second chase ballooned from 9 beats to 17, and the clips broke more often. Every review prompt now stipulates that any suggested fix "has to fit in the shots the film has [...] and never add a shot, a part or a cut."
- **A refused look is a failure.** When a vision model's safety filter blocked a harmless script about a ten-year-old girl, its empty response got parsed as "no problems found". Now, a safety refusal explicitly tells the agent the shot went unchecked.
- **Cap the loop.** Each shot gets reviewed at most three times per user request. Before we added a cap, one runaway session generated 24 images chasing its own reviews.

Reviewing script text instead of rendered pixels didn't work. A text-only continuity checker flagged plenty of script issues without improving the resulting films at all, because most continuity errors arise during generation: an internal cut that forgets where an actor was standing, or a prop that morphs. You can catch those only by looking at the output.

**And the same goes for you.** The evaluations that misled me were the ones that judged text instead of video. One prompt tweak won 15 to 6 when an LLM judge graded the generated prompts, then tied 3 to 4 when grading the actual clips those prompts produced. Today, the only evaluation I trust is watching finished films, blind and in both orders, counting a win only when both pass orders agree. Run identical code against itself twice just to see the baseline variance, which across eight films is large. Re-run your baseline on the same day as your experiment, since hosted models drift. And when testing a single downstream decision, replay saved intermediate states up to that point rather than regenerating whole films from scratch.

**If you're building one**

- Explicitly require habits whose visual payoff the agent can't see. Everywhere else, give facts rather than rules, examples or numbers.
- Trigger visual reviews automatically from the harness, returning findings inside tool results.
- Review full video clips with audio, evaluate the assembled film, and include a blind viewer who hasn't seen the script.
- Treat safety refusals as check failures, cap the review loop, and constrain fixes to existing shots.
- Evaluate your own changes on finished films, never intermediate prompts.

## Last thing

None of these ideas is tied to Doki's script format. Whether you're building a chat agent driving a video API, a node-based canvas or a timeline editor, making a film means coordinating dozens of separate generations, so the agent needs a memory, a plan, a way to change one thing without remaking the rest, and eyes. Video models will absorb parts of this as clips get longer, reference slots multiply and editing improves. What I don't expect to change is that a film is many generations, and that the agent writing it can't see it.

I'm still figuring plenty of this out. If you're building a video agent too, I'd love to hear what's worked for you.
