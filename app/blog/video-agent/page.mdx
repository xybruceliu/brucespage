# Designing a Video Agent That Can Actually Make a Long Film

<p className="text-muted-foreground text-sm">November 2026</p>

Honestly, video models are good now. A single clip often passes for footage, and the newest ones film several shots in one go: [Seedance 2.5](https://seed.bytedance.com/en/blog/one-take-creation-flexible-referencing-introducing-seedance-2-5) makes up to 30 seconds in a single generation, and [MiniMax H3](https://minimax.io/blog/minimax-h3) cuts between shots inside one clip.

However, making a whole film is still hard, even a one-minute one. Most people make it shot by shot on an infinite canvas like [Firefly Boards](https://www.adobe.com/products/firefly/features/boards.html), [FLORA](https://www.florafauna.ai/), [TapNow](https://www.tapnow.ai/) or [LibTV](https://www.liblib.tv/), or in research tools like [VideOrigami](https://arxiv.org/abs/2503.04103) that add a script and a scene planner, and then stitch the takes that work together. Some people hand that loop to a coding agent like [Claude Code](https://www.anthropic.com/product/claude-code), or to the agents these tools now have.

What comes out tends to play like a **slideshow**.

Try making a one-minute film with Claude Code and a video model, and you'll see what I mean. Each shot looks fine on its own but doesn't belong with the one before it. Clips start from a still and stop before the cut, motion and sound don't carry across, and no one planned the rhythm: which moment gets a close-up, which holds, where to cut. Consistency slips too: an old woman's face, or the scarf she knits, changes from shot to shot.

The clips aren't the problem. Today's video agents weren't built for long videos, and their harnesses leave the problems specific to film unsolved: how to plan a scene's shots, what the agent needs to know about film to pace them and write the storyboard, how to keep people, places and looks consistent and the motion continuous across cuts, and how to let the story flow from one scene to the next.

I've been working on these problems in [Doki Agent](https://doki.mov) (Doki's interface is also super interesting, but I'll save it for another post). This post is about the four parts that did most of the work of turning many clips into one film, which I think any video agent needs, however it's built:

1. **Memory**: what has to look the same, and how each generation is told.
2. **Planning**: how a scene is split into generations for the best continuity.
3. **Editing**: how a change reaches the film without re-rolling it.
4. **Feedback**: how the agent reviews what it made and improves it on its own.

Everything below comes from building Doki: the real prompts, what broke, and what fixed it.

## 1. Memory

Doki's memory is a graph of definitions. Every person, place, object and look the film reuses is an entry with a name, a description and a reference image, and entries can use other entries. Before a shot is generated, Doki resolves the graph for that shot and sends the model every definition the shot reaches, in order, with their images. Nothing else carries over: image and video models remember nothing between generations, so anything that exists only as words is drawn anew every time.

### Definitions

An entry is small: a type, a name, a description, and a reference image made from the description. Two from _The Last Three_, one of Doki's example films:

Every shot that uses <T>@Camera</T> is generated with that image, so the tape that reads "3 left" looks the same in all of them.

### Resolving a shot

Entries refer to other entries, so resolving a shot means walking a dependency graph. Here is one shot of _The Last Three_, in which a girl named Mio leaves her last three photos at a shop:

<ResolveFigure />

Doki walks the graph depth-first from everything the shot uses (its own tags, the film-wide look and whatever its section heading adds), emitting each entry after its dependencies:

```ts
const resolve = (tag: Tag) => {
  if (seen.has(tag)) return // each once, so cycles stop
  seen.add(tag)
  tagsIn(tag.definition).forEach(resolve)
  ordered.push(tag) // after everything it uses
}
;[...shot.tags, ...globals, ...fromHeadings].forEach(resolve)
```

The order matters because the prompt lists the definitions in it: by the time the model reads that <T>@WindowPhoto</T> is "<T>@Mio</T> on a train", it already knows who Mio is. The same graph, read backwards, tells you what a change breaks. Change Mio, and every shot that reaches her, directly or through a photo of her, is out of date (section 3).

### Choosing the reference images

Video models take only four to six reference images, and a shot can reach more entries than that, so two rules decide what goes in:

- **The scene so far.** The scene's earlier shots go into every new image, so a scene keeps its place, light and people. This was the biggest consistency win I measured: it cut errors by more than half.
- **What the first frame doesn't show.** A video starts on its first frame, which already shows whoever is on screen, so the slots go first to the rest: the person about to walk in, the place a cut moves to.

Each image is labeled with what the model should take from it, because an unlabeled style reference gets its subject matter copied into the shot:

<Prompt from="Doki's image prompt writer">
  An image that is "the overall style" [...] gives only that quality ("in the
  art style of image 3"). Never put its content in the shot.
</Prompt>

### What gets an entry

Anything seen more than once that should look the same. Leaving this to the agent's judgment failed. An earlier version of my prompt said "characters and key places or objects" get a reference image, and the agent decided a coin, a takeout bag and an orange were simple enough to describe in words, and that a scarf an old woman knits on a train, which a girl wears at the end, "changes form". All of them came out different in every shot. What fixed it was explaining how the models behave instead of naming a category:

<Prompt from="Doki's agent prompt">
  Without one, they get only its text, and each picture draws it anew - each
  shot's image, and each later cut, which has no image of its own: the same
  words come out as a different face, outfit, place or object each time, however
  small or plain it is. [...] So whatever is seen more than once and should look
  the same each time - someone, a place, a vehicle, a prop - gets a definition
  with a reference shot.
</Prompt>

After that change, the scarf got its own entry every time, and continuity errors in my storyboard tests fell by about a fifth.

A reference image also holds everything it shows. If a shop's reference shows it from the street, every shot that uses it pulls toward the street, even the ones set inside. So a place's interior, a costume from another decade or what a character turns into each needs an entry of its own.

### Words beat pictures

When the prompt and a reference image disagree, image models follow the prompt. When our prompt writer gave a character yellow boots, the red ones in her reference vanished. Models also sometimes ignore the images and draw from the text alone: a grandmother the prompt named only by her cardigan came out as a stranger in a cardigan. So Doki's prompt writer adds no looks to anything that has a reference, and describes each person by who they are (age, face, hair, build) before their clothes.

The same goes for the cuts inside a clip, which a model filming several shots at once draws fresh: in half of my test clips, a black-and-white noir turned to color right after the first cut. One sentence fixed it:

<Prompt from="Doki's video prompt writer">
  The video model draws each later shot afresh and drifts from the film's look
  unless told it, so open each shot after the first with the look in a few words
  [...] ("cuts to a close-up, in the same high-contrast black and white: …").
</Prompt>

**If you're building one**

- Anything seen twice that should look the same gets a reference image. Don't leave it to the agent to judge what's important.
- Resolve entries depth-first and list them in dependency order. Keep the graph, since you'll need it in reverse.
- Spend the image budget on the scene so far and on what the first frame doesn't show, and label every image with what to take from it.
- Never add visual details in words to a defined thing. Restate the style at every cut.

## 2. Planning

Planning decides how a scene becomes generations. Newer video models can film several shots in one generation and cut between them, so Doki films a scene's shots together, splits a long scene where the film loses least, and writes each clip's prompt so that the motion carries through its cuts.

The obvious pipeline, one storyboard image and one clip per shot, cut together, is where the slideshow comes from. Each clip starts from a still, its motion and sound start from zero, and left alone it slows to a stop before its cut. Early on, Doki's films looked to me like a beginner splicing clips.

### Film the scene, not the shot

Inside one generation, people, light, motion and sound carry across the cuts, and a reverse angle can show the other side of the room, which separate images struggle with (image models tend to copy the earlier shot's camera position). In my tests, a scene made as one clip beat the same shots made separately in most pairwise comparisons, with about a third fewer continuity breaks.

### Where to split

One clip isn't free, and a scene can run longer than a generation (10 to 30 seconds right now). Inside a clip, only the first shot opens exactly on its storyboard frame; the later ones open close to theirs. A clip boundary resets the motion and the sound instead. Which costs more depends on the cut and the shot: a line of dialogue and its reply shouldn't be split, while a reveal or a product shot needs its exact frame.

So before a scene is filmed, a model reads its shots (the text and the storyboard frames) and rates two things from 0 to 3: for each cut, how much the two sides need to be one take, and for each shot, how much it needs its exact frame. Two lines of the cut rubric:

Each clip has to fit the model's longest generation, a dissolve or fade forces a boundary, and a continuous take is split only when no clip can hold it. ### Writing the clip

A clip's prompt has to give the model something to play, keep it moving, and say it in the model's own terms.

**Open on the first instant.** About 40% of our first frames showed a moment later than the start of the shot. "She walks to the porch, crouches and watches the kitten" produced an image of her already crouched, leaving the clip nothing to play. Image models draw any action the prompt names as already done, so Doki's prompt writer describes the frame as a still photograph, and its answer starts with the opening moment on its own line (`OPENING: she reaches the porch steps`), which forces it to pick a single instant:

<Prompt from="Doki's image prompt writer">
  The image model draws whatever the prompt names as done: an action's verb,
  even with "starting to" or "about to", comes out finished ("starting to sit"
  comes out seated) [...] So write the prompt as a still photograph of that
  instant, in states rather than actions: where each person is, where their
  hands, gaze and weight are, and where each object is.
</Prompt>

**Keep moving through the cut.** The other end of the clip needs the same care. The video prompt writer is told what a stop does to the film:

<Prompt from="Doki's video prompt writer">
  A clip that slows to a stop before its cut makes the film halt there, and when
  every clip does, the film plays like a row of stills. So unless NEXT SHOT is
  none, keep the action and the camera moving through the last second [...]
</Prompt>

**Speak each model's dialect.** MiniMax ignored timed spans like `[2-4s] cut to …` and often cut at around two seconds whatever we wrote. Written in its own shot-list syntax, it cut within a few hundredths of a second of our timestamps:

### What I got wrong

**Count the plans.** For another video model, the calibrated numbers said later shots drift a lot from their storyboard frames, so the planner split scenes much more, giving about half of all shots a clip of their own. Blind comparisons rated these films no better or worse than the fewest-clips plans. Then I watched one myself and saw shots ticking by at 5 seconds, 5 seconds, 5 seconds, just like the old one-clip-per-shot slideshow, and we went back to the fewest clips for that model. An optimum people can't see the reason for looks like a regression, so count what your planner does before you ship it.

**Keep generation limits out of the story.** When the writing agent was told that a scene becomes "one clip, of up to 15s", it stopped writing scenes longer than 15 seconds and split scenes set in one place to fit. A parameter of the planner had leaked into the screenwriting. Once it was told how scenes become clips without the number, its scenes went back to the length the story called for, and the planner handled the splits.

**If you're building one**

- Generate a scene's shots together when the model can, using the model's native shot-list syntax.
- Plan clip boundaries as an optimization over cuts and frames, with losses calibrated per model.
- Make each frame the opening instant, written in states. Keep clips moving through their cuts.
- Hide model duration limits from the writing agent, and count the plans before shipping a planner.

## 3. Editing

Editing treats the film as a build. Every image and clip records what it was made from, a change marks only what depends on it as out of date, and for each of those a judge decides whether to keep it, edit it or remake it, so a fix touches as little of the film as it can.

The default is to regenerate, and that's a coin flip. In our logs, when a review flagged a problem and the shot was made again, the remake fixed it about half the time, and a second try did no better than the first. A remake also throws away what was right: the camera angle, the faces, the take the user approved. Models can edit instead now: give one an image or a clip and an instruction, and it changes what you asked and keeps the rest ([Gemini Omni](https://ai.google.dev/gemini-api/docs/omni) is the one I use for video).

### Staleness is a diff

Whenever Doki generates an image or video, it records the inputs: the shot's text, the resolved definitions, the versions of the reference images and, for a video, the frame it starts on, its timing and the clip it shares. Staleness is a diff between that record and the film as it is now, with reasons ("<T>@Mars</T> changed"). Because definitions resolve through the graph from section 1, a change reaches every shot that depends on it, directly or not. The record is written only after a generation succeeds, so a failed run never marks a shot up to date.

### Keep, edit or remake

For each stale image and video, a fast model compares what the shot was made from with what it says now and picks one of three:

<UpdateFigure />

The judge's prompt is mostly a description of what an edit can and can't do:

<Prompt from="Doki's update judge">
  An edit does a change that sits in the picture: a color, clothes, hair or
  makeup, an object added, removed or swapped, the state an object is in, an
  expression, the light, the weather or the time of day, written text, the
  style. [...] It can't move the camera or change the framing, move people,
  change what they do or how they move, or set the shot somewhere else; in a
  video it can't change what is said, the voices or the timing.
</Prompt>

The edit model sees the pixels but not the script, so the judge writes its instruction in visual terms ("the woman in the red coat"), never in tags. On 62 labeled cases it chose right 61 times. Guardrails in code sit around it: a failed edit falls back to a remake, a shot gets at most three edits in a row, a new image always means a new video, and a photo the user uploaded is never drawn over.

Video edits go to whichever model does them best. Omni kept the motion frame for frame; another model we tried performed the motion again with the change, close but not the same take. So every video edit in Doki goes to Omni, whatever model made the clip.

### Remake the smallest run

When a scene shares one clip, changing one shot shouldn't reshoot the scene. If the change can be an edit, Doki cuts that shot's part out of the clip, edits it, and keeps the result as the shot's own video. If it needs a remake, Doki makes only the run of consecutive shots that need new video and leaves the others alone. The cost is a clip boundary where there wasn't one.

The cheapest fix of all is a trim. Cutting the half second where a hand warps costs nothing, so the agent has a trim tool and is told to fix a shared clip in order of cost: a trim first, then words an edit can follow, and only then the clip again. Doki keeps every version, so a remake that came out worse can be put back.

**If you're building one**

- Record the exact inputs for every generated asset. Staleness is a diff against those inputs, with reasons.
- Triage stale outputs into keep, edit or remake by clearly specifying what an edit model can and can't change.
- Write edit instructions using visible descriptions, never internal tags.
- Prefer a trim to an edit and an edit to a remake, regenerate only the smallest contiguous run, and version everything.

## 4. Feedback

Feedback is a set of reviews the harness runs at fixed points as the agent works: a read of the script, a check of each new picture, a review of the whole film, and a first-time viewer. What they find comes back inside the agent's tool results, so the agent fixes it without being asked.

This has to be designed rather than left to the agent, because even a multimodal agent rarely sees the film it's making. It writes each shot long before that shot exists, it doesn't look at what comes back unless something makes it, and many models still can't watch a video with its sound (in Doki, Gemini does the watching for the agent). Yet almost everything above pays off on screen.

### Reviews the harness runs

We gave the agent a tool to inspect any shot, which has a vision model watch it and answer questions. Across sixteen writing runs, the agent called it on its own zero times. So the reviews run in the harness, the code around the agent that executes its tools:

<ReviewFigure />

In storyboard tests, films made with these reviews won most blind comparisons against films made without them, with about a fifth fewer continuity breaks.

### The first-time viewer

My favorite check is the first-time viewer. The film review has read the script, so it fills in what the pictures leave out. A viewer with no script can't, so wherever their account of the film differs from the script, the film isn't telling the story.

<Prompt from="Doki's first-time viewer">
  Say what you understood, in plain words: [...] What you couldn't follow: who
  someone is or is to someone else, why something happens, where things are,
  what something means, what comes out of nowhere, what you expected that never
  came - each with its shot.
</Prompt>

### What made the reviews work

- **Watch clips, not frames.** Findings from watching whole clips with their sound were real nearly every time, while findings from three sampled frames per clip held up about two times in three. Only whole clips caught a bicycle rolling backward, a hand that never lets go of a cup, or a voice that changed between shots.
- **Tell a gap from a hedge.** The viewer would write that a film "never confirms the boy is him", and the review would ask for a fix, though asked directly, the viewer named the boy right every time. One sentence telling the review that a viewer who understood but hedged has understood removed the false alarms and kept the real catches.
- **Fixes fit the film.** Left alone, the agent answered story critiques by adding beats: a 20-second chase went from 9 beats to 17, and the clips broke more often. Every review is now told that a fix "has to fit in the shots the film has [...] and never add a shot, a part or a cut."
- **A refused look is a failure.** When a vision model's safety filter refused a harmless script about a ten-year-old girl, the empty answer read as "no problems found". Now a refusal tells the agent the shot went unchecked.
- **Cap the loop.** Each shot is reviewed at most three times a request. Before the cap, one run made 24 images chasing its own reviews.

Checking the script instead of the pictures didn't work. A text-only continuity checker flagged plenty in the scripts and changed nothing in the films, because most continuity errors happen in generation: a cut inside a clip that forgets where someone was standing, a prop that morphs. Only looking at the output catches those.

### What the agent is told

The reviews show the agent its work after the fact. Its prompt has to cover the rest: the habits whose payoff it can't see while it writes. In general I prefer agent prompts that say what exists and what it costs, not what to do. Rules get applied mechanically: a rule to "fade in and out of the whole video" faded a tense dialogue scene in and out too. Examples get copied: one sample scene that opened wide and cut close made the agent open twice as many scenes that way. Facts alone worked for most things, but not for consistency. Told only what a reference image does and costs, the agent made almost none. A comment at the top of Doki's agent prompt records why we made an exception:

<Prompt from="Doki's agent prompt, its opening comment">
  [...] the habits whose payoff shows only in images and videos it never sees:
  the three that keep a film consistent (a scene in one paragraph, reference
  shots, an ALL for the shared look) [...] Told only what those do, the agent
  left them out: its films were rows of long single takes.
</Prompt>

When the agent can't see a habit's payoff, state the habit outright or enforce it in code. And keep numbers out of the prompt: a number reads as a target, as the 15-second clip limit did.

### Evaluating the agent itself

The same rule applies to whoever builds the agent: judge the film, not the text. A prompt change that won 15 to 6 when a judge read the prompts tied 3 to 4 on the clips they produced. The only evaluation I trust now is watching finished films, blind and in both orders, and counting a win only when both orders agree. Run identical code against itself to see the noise, which across eight films is large. Rerun the baseline on the same day as the experiment, since hosted models drift. And to test one decision, replay saved runs up to that point instead of regenerating whole films.

**If you're building one**

- Trigger reviews from the harness, and return what they find inside tool results.
- Review whole clips with their sound, review the assembled film, and add a viewer who hasn't seen the script.
- Treat a refusal as a failed check, cap the review loop, and keep fixes within the shots you have.
- State the habits whose payoff the agent can't see. Everywhere else, give it facts rather than rules, examples or numbers.
- Evaluate your changes on finished films, never on prompts.

## Last thing

None of these ideas is tied to Doki's script format. Whether you're building a chat agent driving a video API, a node-based canvas or a timeline editor, making a film means coordinating dozens of separate generations, so the agent needs a memory, a plan, a way to change one thing without remaking the rest, and eyes. Video models will absorb parts of this as clips get longer, reference slots multiply and editing improves. What I don't expect to change is that a film is many generations, and that the agent writing it won't watch it unless you make it.

I'm still figuring plenty of this out. If you're building a video agent too, I'd love to hear what's worked for you.
