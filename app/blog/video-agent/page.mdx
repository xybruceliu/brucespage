# Designing a Video Agent That Can Actually Make a Long Film

<p className="text-muted-foreground text-sm">November 2026</p>

Video models are now genuinely good. A single clip often passes for real footage, and the newest models can film several shots in one generation: [Seedance 2.5](https://seed.bytedance.com/en/blog/one-take-creation-flexible-referencing-introducing-seedance-2-5) produces up to 30 seconds in a single pass, and [MiniMax H3](https://minimax.io/blog/minimax-h3) cuts between shots within one clip.

However, making a whole film, even a one-minute one, remains hard. Most people still work shot by shot: they generate images and clips on an infinite canvas such as [Firefly Boards](https://www.adobe.com/products/firefly/features/boards.html), [FLORA](https://www.florafauna.ai/), [TapNow](https://www.tapnow.ai/) or [LibTV](https://www.liblib.tv/), or in research tools such as [VideOrigami](https://arxiv.org/abs/2503.04103) that add a script and a scene planner, and then assemble the takes that work. Some hand this loop to a coding agent such as [Claude Code](https://www.anthropic.com/product/claude-code), or to the agents these tools now include.

The result tends to play like a **slideshow**.

Try making a one-minute film with Claude Code and a video model, and the problem becomes apparent. Each shot looks fine on its own but does not connect to the one before it. Clips start from a still and stop before the cut, motion and sound do not carry across, and no one has planned the rhythm: which moment gets a close-up, which one holds, and where each cut falls. Consistency slips as well: an old woman's face, or the scarf she knits, changes from shot to shot.

The clips are not the problem. Today's video agents were not designed for long videos, and their harnesses leave the problems specific to film unsolved: how to plan a scene's shots, what film knowledge the agent needs to pace them and write the storyboard, how to keep people, places and looks consistent and motion continuous across cuts, and how to make the story flow from one scene to the next.

I have been working on these problems in [Doki Agent](https://doki.mov) (Doki's interface is also super interesting, and I will cover it in a separate post). This post describes the four components that did most of the work of turning many clips into one film, and that I believe any video agent needs, however it is built:

1. **Definition System**: what has to look the same, and how each generation is set up to keep it consistent.
2. **Shot Planning**: how a scene is split into generations for the best continuity.
3. **Incremental Editing**: how a change reaches the film without re-rolling it.
4. **Review Loop**: how the agent checks what it made and improves it on its own.

A closing section covers the principle behind all four: describe to the agent how the models behave and what the film needs, rather than prescribing rules. The examples below come from building Doki: the actual prompts, what failed, and what fixed it.

## 1. Definition System

A long film must keep its people, places, objects and looks consistent across dozens of generations, yet image and video models retain nothing from one generation to the next. Each generation sees only its own prompt and a few reference images, so anything that exists only as text is redrawn every time. A video agent therefore needs a **definition system**: everything the film reuses is defined once, with a description and a reference image, and every shot references that definition rather than describing it again. Before each generation, the agent resolves the shot's references into the definitions and images the model needs.

### Definitions

A definition has four parts: a type (a character, a place, an object or a look), a name the script can reference, a description, and a reference image generated from that description. Two examples from _The Last Three_, an example film made in Doki:

Every shot that references <T>@Camera</T> is generated with this image, so the tape reading "3 left" looks the same throughout. The image carries most of the consistency; the description is what the image is generated from, and what each prompt repeats.

### Scoping

Definitions differ in how far they reach. A film's visual style should hold in every shot, the weather of one sequence only within that sequence, and a camera move only in the shot that calls for it. A definition system therefore needs scopes, much as style rules in CSS do:

- **Film.** A film-wide definition applies to every shot without being referenced, flashbacks and dreams included. It holds what the whole film shares: its look, its lighting, its mood.
- **Part of the film.** A definition attached to an act, a sequence or a flashback applies to every shot within that part, and to nothing outside it.
- **Shot.** A definition referenced in a shot applies to that shot alone.

Two properties keep scopes predictable. First, reach follows references, not location: where a definition is written does not matter, and it reaches only the shots that reference it, directly or through a scope. Second, scopes accumulate rather than override: a shot that references its own style still receives the film-wide one, so a local choice refines the shared look instead of replacing it.

### Resolving a shot

Definitions can be nested and can depend on other definitions: a photo of Mio on the platform requires both Mio and the platform. The references therefore form a dependency graph, and resolving a shot means traversing it. The following shot from _The Last Three_, in which a girl named Mio leaves her last three photos at a shop, illustrates this:

<ResolveFigure />

Traverse the graph depth-first from the shot's roots, which are its own references plus every film-wide and part-level definition in scope, and emit each definition after the definitions it depends on:

```ts
const resolve = (def: Definition) => {
  if (seen.has(def)) return // each once, so cycles stop
  seen.add(def)
  referencesIn(def.description).forEach(resolve)
  ordered.push(def) // after everything it uses
}
;[...shot.references, ...inScope(shot)].forEach(resolve)
```

The order matters because the prompt lists the definitions in that order: by the time the model reads that <T>@WindowPhoto</T> is "<T>@Mio</T> on a train", it already knows who Mio is. The graph is also worth keeping. Read in reverse, it identifies what a change affects: if Mio changes, every shot that reaches her, directly or through a photo of her, is out of date (Section 3).

### Choosing the reference images

A shot can reach more definitions than a model accepts images (currently four to six for video models), so the agent must choose among them. Two rules proved effective:

- **The scene so far.** Include the scene's earlier shots with every new image, so the scene keeps its place, lighting and people. This was the largest consistency improvement I measured, reducing errors by more than half.
- **What the first frame does not show.** A video starts from its first frame, which already shows whoever is on screen. Spend the remaining slots on what it omits: the person about to enter, or the place a cut leads to.

Each image should be labeled with what the model is to take from it. An unlabeled style reference has its subject matter copied into the shot:

<Prompt from="Doki's image prompt writer">
  An image that is "the overall style" [...] gives only that quality ("in the
  art style of image 3"). Never put its content in the shot.
</Prompt>

### What gets a definition

Anything that appears more than once and should look the same, however small. This decision should not be left to the agent. An earlier version of my prompt stated that "characters and key places or objects" receive a reference image, and the agent decided that a coin, a takeout bag and an orange were simple enough to describe in words, and that a scarf an old woman knits on a train, which a girl wears at the end, "changes form". All of them came out differently in every shot. What fixed this was explaining how the models behave, rather than naming a category:

<Prompt from="Doki's agent prompt">
  Without one, they get only its text, and each picture draws it anew - each
  shot's image, and each later cut, which has no image of its own: the same
  words come out as a different face, outfit, place or object each time, however
  small or plain it is. [...] So whatever is seen more than once and should look
  the same each time - someone, a place, a vehicle, a prop - gets a definition
  with a reference shot.
</Prompt>

After this change, the scarf received its own definition in every run, and continuity errors in my storyboard tests fell by about a fifth.

A reference image also fixes everything it shows. If a shop's reference shows its exterior, every shot that uses it is pulled toward the exterior, including shots set inside. A place's interior, a costume from another period, or what a character transforms into therefore each needs a definition of its own.

### Text overrides images

When the prompt and a reference image disagree, image models follow the prompt. If the text gives a character yellow boots, the red boots in her reference disappear. Models also occasionally ignore the images and draw from the text alone: a grandmother whom the prompt identified only by her cardigan came out as a stranger wearing a cardigan. The prompt should therefore add no appearance details to anything that has a reference, and should describe each person by who they are (age, face, hair, build) before their clothing.

The same applies to cuts within a clip, which a model filming several shots in one generation draws afresh: in half of my test clips, a black-and-white noir turned to color immediately after the first cut. A single sentence in the video prompt fixed this:

<Prompt from="Doki's video prompt writer">
  The video model draws each later shot afresh and drifts from the film's look
  unless told it, so open each shot after the first with the look in a few words
  [...] ("cuts to a close-up, in the same high-contrast black and white: …").
</Prompt>

**If you're building one**

- Give a definition with a reference image to everything that appears more than once and should look the same. Do not leave it to the agent to judge what is important.
- Scope definitions to the whole film, a part of it or a single shot, and let scopes accumulate rather than override.
- Resolve definitions depth-first and list them in dependency order. Keep the graph, since you will need it in reverse.
- Spend the image budget on the scene so far and on what the first frame does not show, and label every image with what to take from it.
- Never add visual details in text to a defined element. Restate the style at every cut.

## 2. Shot Planning

This section relies on three units of film. A **shot** is one continuous view from one camera position, lasting until a **cut** switches to the next. A **scene** is a run of shots in one place and time: in _The Last Three_, one scene on a snowy train platform opens with Mio raising her film camera, cuts to a close-up of Haruto looking back, and then to the camera tumbling into the snow. A **clip** is what one video generation returns.

The slideshow effect originates in the obvious pipeline: one storyboard image and one clip per shot, cut together. Each clip starts from a still, its motion and sound start from zero, and, unconstrained, it slows to a stop before its cut. A video agent needs a planner instead: one that decides which shots are filmed together in a single generation, where a long scene is split into clips, and how each clip's prompt keeps the motion going through its cuts.

### Film the scene, not the shot

On a film set, a scene's shots are also filmed one at a time, but they share one physical world. The set, the actors and the light are the same from one shot to the next, a continuity supervisor checks that every object is where it was, and the editor cuts in the middle of an action so that a movement begun in one shot finishes in the next. That shared world is what lets separate shots read as one continuous moment.

A video model has no such world. Each generation invents its own, so a scene generated one shot per clip is several slightly different worlds cut together. On the platform, the snowfall and the light would shift at every cut, and the camera that slips in one clip would start the next from a standstill, with the sound of the station starting again from silence.

Recent video models can film several shots in one generation and cut between them, which restores the shared world within that generation. When the model cuts from Mio to Haruto, the platform, the light and the snow are the ones it has just drawn; when it cuts to the camera, the camera is still falling, and the sound carries across both cuts. The model can also turn the camera around: a reverse angle shows the other side of the platform, which separately generated images handle poorly, since image models tend to copy the earlier shot's camera position.

The unit of generation should therefore be the scene, not the shot. In my tests, a scene generated as one clip outperformed the same shots generated separately in most pairwise comparisons, with about a third fewer continuity breaks.

### Where to split

A single clip has costs of its own, and a scene can exceed the length of one generation (currently 10 to 30 seconds). Within a clip, only the first shot opens exactly on its storyboard frame; later shots open only approximately on theirs. A clip boundary, in turn, resets the motion and the sound. Which cost is greater depends on the cut and the shot: a line of dialogue and its reply should not be split, while a reveal or a product shot needs its exact frame.

Before filming a scene, therefore, have a model read its shots (both the text and the storyboard frames) and rate two quantities from 0 to 3: for each cut, how strongly the two sides need to form one take, and for each shot, how strongly it needs its exact frame. Two levels of the cut rubric:

### Writing the clip

A clip's prompt must give the model something to play, keep it moving, and express both in the model's own conventions.

**Open on the first instant.** In about 40% of our first frames, the image showed a later moment than the start of the shot. "She walks to the porch, crouches and watches the kitten" produced an image of her already crouched, leaving the clip nothing to play. Image models render any action the prompt names as already completed, so the frame should be described as a still photograph, with the prompt writer stating the opening moment on its own line first (`OPENING: she reaches the porch steps`), which forces it to commit to a single instant:

<Prompt from="Doki's image prompt writer">
  The image model draws whatever the prompt names as done: an action's verb,
  even with "starting to" or "about to", comes out finished ("starting to sit"
  comes out seated) [...] So write the prompt as a still photograph of that
  instant, in states rather than actions: where each person is, where their
  hands, gaze and weight are, and where each object is.
</Prompt>

**Keep moving through the cut.** The end of the clip requires the same care. The video prompt writer is told what a stop does to the film:

<Prompt from="Doki's video prompt writer">
  A clip that slows to a stop before its cut makes the film halt there, and when
  every clip does, the film plays like a row of stills. So unless NEXT SHOT is
  none, keep the action and the camera moving through the last second [...]
</Prompt>

**Speak each model's dialect.** MiniMax ignored timed spans such as `[2-4s] cut to …` and often cut at around two seconds regardless of the prompt. Written in its own shot-list syntax, it cut within a few hundredths of a second of the specified timestamps:

### What I got wrong

**Count the plans.** For another video model, the calibrated values indicated that later shots drift far from their storyboard frames, so the planner split scenes much more often, giving about half of all shots their own clip. Blind comparisons rated these films neither better nor worse than fewest-clip plans. When I watched one, however, the shots ticked by at 5 seconds, 5 seconds, 5 seconds, exactly like the old one-clip-per-shot slideshow, and we reverted that model to the fewest clips. An optimum whose rationale users cannot see looks like a regression, so inspect what a planner produces before shipping it.

**Keep generation limits out of the story.** When the writing agent was told that a scene becomes "one clip, of up to 15s", it stopped writing scenes longer than 15 seconds and split single-location scenes to fit. A planner parameter had leaked into the screenwriting. Once the agent was told how scenes become clips, without the number, its scenes returned to the length the story required, and the planner handled the splits.

**If you're building one**

- Generate a scene's shots together when the model supports it, using the model's native shot-list syntax.
- Plan clip boundaries as an optimization over cuts and frames, with losses calibrated per model.
- Make each frame the opening instant, written in states, and keep clips moving through their cuts.
- Hide model duration limits from the writing agent, and inspect the plans before shipping a planner.

## 3. Incremental Editing

A long film is never right on the first attempt, and it keeps changing during production: a character's hair, a planet that should be frozen, a new line of dialogue. The default response is to regenerate whatever a change touches, which is unreliable. In my logs, when a review flagged a problem and the shot was regenerated, the remake fixed it about half the time, and a second attempt did no better than the first. Each remake also discards what was correct: the camera angle, the faces, the take the user approved.

A video agent should instead treat the film as a build system: determine exactly what is out of date, and rebuild as little as possible, editing wherever it can. Current models support editing: given an image or a clip and an instruction, they change what was requested and preserve the rest ([Gemini Omni](https://ai.google.dev/gemini-api/docs/omni) is the model I use for video).

### Staleness is a diff

For every image and clip, record its inputs: the shot's text, the resolved definitions, the versions of the reference images and, for a video, its starting frame, its timing and the clip it shares. Staleness is then a diff between that record and the current state of the film, with reasons attached ("<T>@Mars</T> changed"). Because definitions are resolved through the graph from Section 1, a change propagates to every shot that depends on it, directly or indirectly. Write the record only after a generation succeeds, so that a failed run never marks a shot as up to date.

### Keep, edit or remake

For each stale image and video, have a fast model compare its recorded inputs with the shot's current state and choose one of three actions:

Most of the judge's prompt specifies what an edit can and cannot do:

<Prompt from="Doki's update judge">
  An edit does a change that sits in the picture: a color, clothes, hair or
  makeup, an object added, removed or swapped, the state an object is in, an
  expression, the light, the weather or the time of day, written text, the
  style. [...] It can't move the camera or change the framing, move people,
  change what they do or how they move, or set the shot somewhere else; in a
  video it can't change what is said, the voices or the timing.
</Prompt>

The edit model sees the pixels but not the script, so the judge must write its instruction in visual terms ("the woman in the red coat") rather than in tags. On 62 labeled cases, Doki's judge chose correctly 61 times. Guardrails in code surround it: a failed edit falls back to a remake, a shot receives at most three consecutive edits, a new image always triggers a new video, and a photo uploaded by the user is never overwritten.

Route video edits to the model that performs them best. Omni preserved the original motion frame for frame; another model we tested re-performed the motion with the change, which looked similar but was no longer the same take. Every video edit in Doki therefore goes to Omni, regardless of which model generated the clip.

### Remake the smallest run

When a scene shares one clip, changing one shot should not regenerate the whole scene. If the change can be made as an edit, extract that shot's segment from the clip, edit it, and keep the result as the shot's own video. If it requires a remake, regenerate only the run of consecutive shots that need new video, and leave the others unchanged. The cost is a clip boundary where there was none.

The cheapest fix is a trim. Removing the half second in which a hand warps costs nothing, so give the agent a trim tool and instruct it to repair a shared clip in order of cost: first a trim, then a rewording that an edit can follow, and only then a regeneration. Keep every version, so that a remake that turns out worse can be reverted.

**If you're building one**

- Record the exact inputs of every generated asset. Staleness is a diff against those inputs, with reasons.
- Triage stale outputs into keep, edit or remake by specifying precisely what an edit model can and cannot change.
- Write edit instructions in visual descriptions, never in internal tags.
- Prefer a trim to an edit and an edit to a remake, regenerate only the smallest contiguous run, and version everything.

## 4. Review Loop

A video agent cannot fix what it does not see, and even a multimodal agent rarely sees the film it is making. It writes each shot long before that shot exists, it does not inspect the results unless something requires it to, and many models still cannot watch a video with its sound (in Doki, Gemini watches on the agent's behalf). Yet nearly everything described above pays off on screen. The agent therefore needs a review loop built into its harness: reviews that run at fixed points as it works, and whose findings are returned in its tool results.

### Reviews the harness runs

The agent cannot be relied on to look on its own. I gave Doki's agent a tool to inspect any shot, in which a vision model watches the shot and answers questions; across sixteen writing runs, the agent invoked it unprompted zero times. The reviews therefore run in the harness, the code around the agent that executes its tools:

In storyboard tests, films produced with these reviews won most blind comparisons against films produced without them, with about a fifth fewer continuity breaks.

### The first-time viewer

The check I value most is the first-time viewer: a model that watches the finished film without the script or the request, and reports what it understood. The film review has read the script, so it fills in what the images leave out. The viewer cannot, so wherever its account differs from the script, the film is failing to tell the story.

<Prompt from="Doki's first-time viewer">
  Say what you understood, in plain words: [...] What you couldn't follow: who
  someone is or is to someone else, why something happens, where things are,
  what something means, what comes out of nowhere, what you expected that never
  came - each with its shot.
</Prompt>

### What makes reviews work

- **Watch clips, not frames.** Findings from watching whole clips with sound were accurate nearly every time, whereas findings from three sampled frames per clip held up about two times in three. Only whole clips revealed a bicycle rolling backward, a hand that never lets go of a cup, or a voice that changed between shots.
- **Distinguish a gap from a hedge.** The viewer would write that a film "never confirms the boy is him", and the review would request a fix, although, when asked directly, the viewer identified the boy correctly every time. One sentence telling the review that a viewer who understood but hedged has understood eliminated the false alarms while preserving the genuine findings.
- **Fixes must fit the film.** Unconstrained, the agent responded to story critiques by adding beats: a 20-second chase grew from 9 beats to 17, and the clips broke more often. Every review should state that a fix "has to fit in the shots the film has [...] and never add a shot, a part or a cut."
- **A refused review is a failure.** When a vision model's safety filter refused a harmless script about a ten-year-old girl, the empty response was read as "no problems found". A refusal should instead tell the agent that the shot went unchecked.
- **Cap the loop.** Review each shot at most three times per request. Before the cap, one run generated 24 images in pursuit of its own reviews.

Reviewing the script instead of the images does not work. A text-only continuity checker flagged many issues in the scripts and changed nothing in the films, because most continuity errors arise during generation: a cut within a clip that forgets where someone was standing, or a prop that morphs. Only inspecting the output catches them.

### Evaluating the agent itself

The same principle applies to whoever builds the agent: evaluate the film, not the text. A prompt change that won 15 to 6 when a judge read the prompts tied 3 to 4 on the clips they produced. The only evaluation I now trust is watching finished films, blind and in both orders, counting a win only when both orders agree. Run identical code against itself to measure the noise, which across eight films is large. Rerun the baseline on the same day as the experiment, since hosted models drift. To test a single decision, replay saved runs up to that point rather than regenerating whole films.

**If you're building one**

- Trigger reviews from the harness, and return their findings in tool results.
- Review whole clips with their sound, review the assembled film, and include a viewer who has not seen the script.
- Treat a refusal as a failed check, cap the review loop, and keep fixes within the existing shots.
- Evaluate changes on finished films, never on prompts.

## Describe, Don't Prescribe

One principle runs through all four components: tell the agent how the models behave and what the film needs, rather than giving it rules, examples or heuristics to follow. A prompt that describes the system lets the agent reason about cases the prompt never anticipated; a prompt that prescribes is followed literally, including where it no longer applies.

Prescriptions fail in predictable ways. Rules are applied mechanically: a rule to "fade in and out of the whole video" also faded a tense dialogue scene in and out. Examples are copied: one sample scene that opened wide and then cut close made the agent open twice as many scenes that way. Numbers become targets: told that a scene becomes "one clip, of up to 15s", the agent cut its scenes to fit (Section 2). Categories invite the agent to judge them: "characters and key places or objects" left it to decide that a coin or a scarf was not key (Section 1).

The fixes in this post are descriptions instead. The agent prompt explains that each picture draws an undefined thing anew, however small or plain (Section 1). The video prompt writer is told what a stop before the cut does to the film, and when a stop is right: at the end of a scene, or on a held moment (Section 2). The update judge is told what an edit can and cannot change, and decides each case itself (Section 3).

There is one exception. Facts alone failed for consistency: told only what a reference image does and costs, the agent created almost none, because the payoff appears only in images and videos it never sees while it writes. A habit whose payoff the agent cannot observe has to be stated outright, or enforced in code. A comment at the top of Doki's agent prompt records the reasoning:

<Prompt from="Doki's agent prompt, its opening comment">
  [...] the habits whose payoff shows only in images and videos it never sees:
  the three that keep a film consistent (a scene in one paragraph, reference
  shots, an ALL for the shared look) [...] Told only what those do, the agent
  left them out: its films were rows of long single takes.
</Prompt>

**If you're building one**

- Tell the agent what exists, how the models behave and what each choice costs, not what to do.
- Leave out rules, examples, numbers and categories the agent would have to interpret: each is followed literally.
- State outright the habits whose payoff the agent cannot see, or enforce them in code.

## Looking ahead

None of these ideas is specific to Doki's script format. Whether the agent is a chat agent driving a video API, a node-based canvas or a timeline editor, making a film means coordinating dozens of separate generations, so it needs a definition system, a shot planner, incremental editing and a review loop. Video models will absorb parts of this as clips grow longer, reference slots multiply and editing improves. What I do not expect to change is that a film consists of many generations, and that the agent writing it will not watch it unless something makes it.

I am still working through much of this. If you are building a video agent as well, I would like to hear what has worked for you.
