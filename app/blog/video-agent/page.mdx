# Designing a Video Agent That Can Actually Make a Long Film

<p className="text-muted-foreground text-sm">November 2026</p>

Video models are now genuinely good. A single clip often looks like real footage, and the newest models can film several shots in one generation. [Seedance 2.5](https://seed.bytedance.com/en/blog/one-take-creation-flexible-referencing-introducing-seedance-2-5) produces up to 30 seconds in a single pass, and [MiniMax H3](https://minimax.io/blog/minimax-h3) cuts between shots within one clip.

However, making a whole film remains hard, even for a one-minute video. Most people still work shot by shot. They generate images and clips on an infinite canvas such as [Firefly Boards](https://www.adobe.com/products/firefly/features/boards.html), [FLORA](https://www.florafauna.ai/), [TapNow](https://www.tapnow.ai/) or [LibTV](https://www.liblib.tv/), or in research tools such as [VideOrigami](https://arxiv.org/abs/2503.04103) that add a script and a scene planner. Then they assemble the takes that work. Some people hand this workflow to a coding agent such as [Claude Code](https://www.anthropic.com/product/claude-code), or to the built-in agents in these tools.

The result tends to play like a **slideshow**.

If you try to make a one-minute film with Claude Code and a video model, you will quickly see the problem. Each shot looks fine on its own, yet it does not connect to the shot before it. Clips start from a still image and stop before the cut, so motion and sound do not carry across cuts. Nothing plans the rhythm of the film: which moment gets a close-up, which shot holds, and where each cut falls. Visual consistency slips as well. An old woman's face or the scarf she knits changes from shot to shot.

Individual clip quality is no longer the bottleneck. Current video agents were not designed for long videos, so their harnesses (the code that runs the agent and its tools) leave the problems specific to film unsolved. Nothing in them plans the shots in a scene or supplies the film knowledge needed to pace those shots and write a storyboard. Nothing keeps people, places and visual styles consistent, keeps motion continuous across cuts, or makes the story flow from one scene to the next.

I have been working on these problems in [Doki Agent](https://doki.mov) (Doki's interface is also super interesting, and I will cover it in a separate post). This post describes the four components that did most of the work to turn many clips into one coherent film. I believe any video agent needs these four parts, regardless of how it is built:

1. **Definition System**: how the agent tracks things that must look the same, and how it sets up each generation to keep them consistent.
2. **Shot Planning**: how the agent splits a scene into video generations for the best continuity.
3. **Incremental Editing**: how the agent applies a change to the film without regenerating everything from scratch.
4. **Review Loop**: how the agent checks what it made and improves the film on its own.

A closing section covers the principle behind all four: describe to the agent how the models behave and what the film needs, instead of prescribing rules. The examples come from Doki, with its actual prompts and algorithms.

## 1. Definition System

A long film must keep its people, places, objects and visual styles consistent across dozens of generations. However, image and video models remember nothing from one generation to the next. Each generation sees only its own prompt and a few reference images, so the model redraws anything described only in text every time. A video agent therefore needs a **definition system**. Everything the film reuses is defined once, with a text description and a reference image, and every shot references that definition instead of describing the item again. Before each generation, the agent resolves the shot's references: it collects the definitions and reference images the shot uses and passes them to the model.

### Definitions

A definition has four parts: a type (character, place, object or look), a name that the script can reference, a text description, and a reference image generated from that description. Here are two examples from a short film made in Doki:

<Definitions />

Every shot that references <T>@Camera</T> is generated with this reference image, so the tape reading "3 left" looks the same throughout the film. The image provides most of the consistency. The description is what the image is generated from, and each shot's prompt repeats it.

### Scoping

Different definitions apply to different parts of the film. A film's visual style should apply to every shot, the weather of one sequence only within that sequence, and a specific camera move only to a single shot. A definition system therefore needs scopes, much like style rules in CSS:

- **Film.** A film-wide definition applies to every shot automatically, including flashbacks and dreams, even when a shot does not reference it. It holds what the whole film shares, such as its visual style, lighting and mood.
- **Part of the film.** A definition attached to an act, a sequence or a flashback applies to every shot inside that part, and to nothing outside it.
- **Shot.** A definition referenced in a single shot applies to that shot alone.

Two rules keep scopes predictable. First, a definition applies only where it is referenced or scoped, regardless of where it is written. Second, scopes add together instead of overriding one another. If a shot references its own visual style, it still receives the film-wide style, so the shot's choice refines the shared look instead of replacing it.

### Resolving a shot

Definitions can be nested and can depend on other definitions. For example, a photo of a character on a train platform depends on both the character and the platform. These references form a dependency graph, so resolving a shot means walking that graph. In the shot below, a close-up of three photos on a shop counter, each photo is a definition that references other definitions:

<ResolveFigure />

The agent walks the graph depth-first, starting from the shot's own references and every film-wide or part-level definition in scope. It outputs each definition after the definitions it depends on:

```ts
const resolve = (def: Definition) => {
  if (seen.has(def)) return // each once, so cycles stop
  seen.add(def)
  referencesIn(def.description).forEach(resolve)
  ordered.push(def) // after everything it uses
}
;[...shot.references, ...inScope(shot)].forEach(resolve)
```

This order matters because the prompt lists the definitions in the same order. By the time the model reads that a photo shows a character on a train, it has already read who that character is. The graph is also worth keeping. Read in reverse, it shows what a change affects. If a character changes, every shot that uses that character, directly or through a photo of them, is out of date (Section 3).

### Choosing the reference images

A shot can use more definitions than a model accepts as reference images, and video models currently accept four to six. So the agent must choose which images to send. Two rules worked well:

- **The scene so far.** When generating a new image, include the images of the earlier shots in the same scene, so the place, lighting and people stay the same. This was the largest consistency improvement I measured: it cut continuity errors by more than half.
- **What the first frame does not show.** A video starts from its first frame, which already shows everyone and everything on screen. Use the remaining slots for what that frame leaves out, such as a person who is about to enter or the place a cut leads to.

Each reference image also needs a label that says what the model should take from it. A style reference without a label gets its content copied into the shot:

<Prompt from="Doki's image prompt writer">
  An image that is "the overall style" [...] gives only that quality ("in the
  art style of image 3"). Never put its content in the shot.
</Prompt>

### What gets a definition

Anything that appears more than once and must look the same needs a definition, however small or plain it is. A coin, a takeout bag or a scarf without a definition is redrawn from its words in every shot, and it comes out different each time. So the agent should not be the one to decide which items are important enough. Doki's agent prompt makes this clear by explaining how the models behave:

<Prompt from="Doki's agent prompt">
  Without one, they get only its text, and each picture draws it anew - each
  shot's image, and each later cut, which has no image of its own: the same
  words come out as a different face, outfit, place or object each time, however
  small or plain it is. [...] So whatever is seen more than once and should look
  the same each time - someone, a place, a vehicle, a prop - gets a definition
  with a reference shot.
</Prompt>

A reference image also locks in every visual detail it shows. If a shop's reference image shows the outside of the building, every shot that uses it is pulled toward an exterior view, even when the shot is set inside the shop. So a building's interior, a costume from another time period, and a new form that a character transforms into each need a definition of their own.

### Text overrides images

When the text prompt and a reference image disagree, image models follow the text. If the prompt says a character wears yellow boots, the red boots in her reference image disappear. Models also sometimes ignore the reference images and draw from the text alone, so a grandmother described only by her cardigan can come out as a different woman in a cardigan. The prompt should therefore never add visual details to anything that has a reference image. It should describe each person by who they are (age, face, hair and build) before their clothing.

The same is true at the cuts inside a multi-shot clip. The video model draws each shot after a cut from scratch, so the film's look drifts: a black-and-white scene can turn to color right after the first cut. The video prompt should restate the look at every cut:

<Prompt from="Doki's video prompt writer">
  The video model draws each later shot afresh and drifts from the film's look
  unless told it, so open each shot after the first with the look in a few words
  [...] ("cuts to a close-up, in the same high-contrast black and white: …").
</Prompt>

**If you're building one**

- Create a definition with a reference image for everything that appears more than once and should look the same, and do not let the agent judge which items are important enough.
- Scope definitions to the whole film, a part of it or a single shot, and make scopes add together rather than override one another.
- Walk the definition graph depth-first and list the definitions in dependency order. Keep the graph, so you can trace a change in reverse.
- Spend the reference image slots on the scene so far and on what the first frame leaves out, and label every image with what to take from it.
- Never add appearance details in text to something that has a definition, and restate the look at every cut.

## 2. Shot Planning

This section uses a few filmmaking terms. A **shot** is one continuous view from a single camera position until a **cut** switches to the next view. A **scene** is a sequence of shots in one place and time, such as a dinner-table conversation that cuts back and forth between two speakers a dozen times. A **clip** is the video that one generation returns.

Most video agents make films that look like a slideshow, because they generate one clip per shot and stitch the clips together. Each clip starts from a still image, so its motion and sound start from zero, and it tends to slow to a stop before its cut. A video agent needs a shot planner instead. The planner decides which shots to generate together in one clip and where to split a long scene into several clips, and the clip prompts keep the motion going across each cut.

### Film the scene, not the shot

On a real film set, a crew also films a scene one shot at a time, yet all those shots share the same physical world. The set, the actors and the lighting stay the same from shot to shot. A continuity supervisor checks that props stay where they were, and the editor cuts in the middle of an action, so a movement that starts in one shot finishes in the next. That shared world makes separate shots feel like one continuous moment.

A video model has no shared world across separate generations. Each generation invents a new world from scratch, so generating one clip per shot pieces together several slightly different worlds. The lighting and background shift at every cut, movements restart from a standstill, and the sound restarts from silence.

Recent video models can generate several shots in one pass and cut between them, which gives those shots a shared world again. After each cut, the model keeps the people, the place and the lighting it just drew, and movement and sound carry across the cut. Multi-shot generation also handles reverse angles better. When the camera turns around to show the other side of a room, separately generated images often fail, because image models tend to copy the camera angle of the previous shot.

<SceneFigure />

The basic unit of video generation should therefore be the scene, not the single shot. In my tests, generating a scene as one multi-shot clip beat generating its shots separately in most head-to-head comparisons, with about a third fewer continuity breaks.

### Why a scene still needs a plan

Generating a scene as one clip is not free, and it is not always possible:

- **Length.** A model can only generate so much at once, currently 10 to 30 seconds, and many scenes run longer.
- **Drift from the storyboard.** A clip starts exactly on its first shot's storyboard frame. The model then draws every later shot itself, guided by the text and the reference images, so those shots only come close to their frames.
- **A fresh start at each boundary.** A new clip opens exactly on its own first frame, but its motion, its people and its sound start over.

So every cut poses a question: is it worse to break the take here, or to let the next shot drift from its frame? The answer depends on the cut and the shot. Breaking a line of dialogue from its reply hurts, while breaking where the story jumps to a new place costs nothing. A reaction shot works fine if it only comes close to its storyboard frame, while a reveal, a product shot or the user's own photo must open exactly on its frame. Every extra clip also costs money.

### A model judges, an algorithm decides

The planning problem has two parts, and they suit different tools. Rating what each cut and each shot needs is a matter of taste: it requires reading the story and looking at the frames. A language model does this well. Choosing the best split is an optimization with hard limits, and the choice at one cut changes what every other cut costs. A language model does this poorly, but a short algorithm does it exactly. On 11 hard scenes, Doki's plans made this way passed 32 of 32 editing checks, while plans that Gemini wrote directly passed 79 to 85% of them.

**Reading the scene.** Before a scene's video is made, a model reads the scene, both the shots' text and their storyboard frames, and rates each cut and each shot from 0 to 3:

<Rubric />

The frames matter. They show details the text may leave out, such as an engraving that must be legible, or two shots in a row with nearly the same view. Rated from the words alone, the same scenes passed 28 of the 32 checks. The levels also describe the film, not the video model, so one reading works for any model. What each level costs is measured separately for each model.

**Choosing the split.** Each cut in a scene either becomes a clip boundary or does not, so a scene of n shots can be split 2<sup>n−1</sup> ways. A small dynamic program finds the best split without trying them all. Let best[j] be the lowest loss of any plan for the first j shots. The last clip of that plan covers shots i+1 through j for some i, so best[j] is the best value of best[i] plus what that last clip loses:

<Formula />

The clip pays a penalty S at the cut before it, based on how much that cut needs to stay in one continuous clip. It pays a penalty F for each shot after the first, based on how much each shot needs to open exactly on its storyboard frame. It also pays its price, at half a point per dollar. A clip longer than the model allows is never considered, a dissolve or a fade always starts a new clip, and a continuous take with no cut is split only when no clip can hold it. When two plans tie, the longer clip wins.

**Measuring the costs.** S and F are measured in the same unit, points on a judge's 1-to-10 rating, so the planner can weigh one directly against the other. To measure them, I generated each test scene twice, once in as few clips as the length limit allows and once with a separate clip for every shot. A model then rated every cut and shot that differed between the two versions, side by side. For MiniMax H3, a cut rated 2 or 3 scored 1.2 points better inside one clip, while a cut rated 0 or 1 scored no better. A shot rated 2 or 3 lost 1.2 points when it came later in a clip instead of starting its own, while one rated 0 or 1 lost nothing. With this table, the planner predicted which whole film the judge preferred in 8 of 10 scenes. A model that has not been measured gets a flat table: every clip boundary costs the same, and drifting from a frame costs nothing. Its plans are simply the fewest clips that fit.

Here is the planner on the whole platform scene from Fig. 2. The scene runs 20 seconds, longer than MiniMax's limit of 15, so it needs at least two clips. Of the 16 possible splits, 13 fit. The best one breaks before s4, at a cut rated 2, so s4 opens exactly on its frame, which it needs. Breaking one cut earlier, as the camera starts to fall, would split a moment rated 3 and lose more:

The agent that writes the script never sees any of this. It writes each scene at the length the story needs, and the planner decides how the scene becomes clips. Generation limits stay out of the story.

### Writing the clip

Once the clips are planned, each one needs two prompts: an image prompt for its first frame and a video prompt for its motion. Both must give the model something to play and keep it moving.

**Open on the first instant.** Image models draw any action the prompt names as already done. "She walks to the porch, crouches and watches the kitten" comes out with her already crouched, and the clip has nothing left to play. So the image prompt should describe a still photograph of the shot's first instant, in states rather than actions. Doki's prompt writer first names that instant on its own line (`OPENING: she reaches the porch steps`), which forces the writer to commit to a single moment:

<Prompt from="Doki's image prompt writer">
  The image model draws whatever the prompt names as done: an action's verb,
  even with "starting to" or "about to", comes out finished ("starting to sit"
  comes out seated) [...] So write the prompt as a still photograph of that
  instant, in states rather than actions: where each person is, where their
  hands, gaze and weight are, and where each object is.
</Prompt>

**Keep moving through the cut.** Video models tend to slow to a stop at the end of a clip. Doki's video prompt writer is told what that does to the film:

<Prompt from="Doki's video prompt writer">
  A clip that slows to a stop before its cut makes the film halt there, and when
  every clip does, the film plays like a row of stills. So unless NEXT SHOT is
  none, keep the action and the camera moving through the last second [...]
</Prompt>

**Translate the plan for each model.** Keep the plan itself independent of the model: a list of shots with their timings. Then write it out in each video model's own syntax, because models read prompts differently. MiniMax ignores timed spans such as `[2-4s] cut to …` and often cuts at around two seconds regardless. Written in its own shot-list syntax, it cuts within a few hundredths of a second of each timestamp:

Each model also has quirks that the right wording fixes. These are the ones I met most often:

**If you're building one**

- Generate a scene's shots together in one clip whenever the model supports it.
- Let a model rate what each cut and shot needs, and let an algorithm choose the split, with costs measured for each video model.
- Write each first frame as a still photograph of the opening instant, and keep each clip moving through its cuts.
- Keep the plan independent of the model, write it in each model's own syntax, and keep generation limits out of the script.

## 3. Incremental Editing

A long film is never right on the first try. Details keep changing during production: a character's hairstyle, a planet that should be frozen, a new line of dialogue. The obvious response is to regenerate every shot a change touches, but regeneration is a gamble. In my logs, regenerating a shot fixed the flagged problem only about half the time. It also throws away what was already right: the camera angle, the faces, the take the user approved.

A video agent should instead treat the film like a software build. It tracks exactly which assets are out of date and rebuilds as little as possible, editing wherever it can. Current image and video models support editing: given an image or a clip and an instruction, they change what was asked and keep the rest.

### Staleness is a diff

For every image and clip, record the inputs that made it: the shot's text, the resolved definitions, the versions of the reference images, and for a video, its first frame, its timing and the clip it shares with other shots. An asset is stale when its record differs from the current state of the film, and the difference is the reason ("<T>@Mars</T> changed"). Because definitions are resolved through the graph from Section 1, a change to one definition reaches every shot that depends on it, directly or indirectly. Write the record only after a generation succeeds, so a failed run never marks a shot as up to date.

### Keep, edit or remake

For each stale image or clip, a fast model compares the recorded inputs with the shot's new state and chooses one of three actions: keep the asset, edit it, or remake it:

<UpdateFigure />

Most of the judge's prompt describes what an edit can and cannot change:

<Prompt from="Doki's update judge">
  An edit does a change that sits in the picture: a color, clothes, hair or
  makeup, an object added, removed or swapped, the state an object is in, an
  expression, the light, the weather or the time of day, written text, the
  style. [...] It can't move the camera or change the framing, move people,
  change what they do or how they move, or set the shot somewhere else; in a
  video it can't change what is said, the voices or the timing.
</Prompt>

The edit model sees only the image or video, not the script, so the judge writes its instruction in visual terms ("the woman in the red coat") rather than definition names. On 62 labeled cases, Doki's judge chose correctly 61 times. Rules that must always hold stay in code rather than in the judge: a failed edit falls back to a remake, and a photo the user uploaded is never overwritten.

Send every video edit to an editing model that preserves the original footage, regardless of which model generated the clip. Doki uses [Gemini Omni](https://ai.google.dev/gemini-api/docs/omni), which changes what was asked and keeps the motion frame for frame.

### Remake the smallest run

When several shots share one clip, changing one of them should not regenerate the whole scene. If the change can be an edit, cut that shot's segment out of the clip, edit it, and keep the result as that shot's own video. If the shot needs a remake, regenerate only the run of neighboring shots that need new video, and leave the rest of the clip as it is. The cost is a new clip boundary where there was none before.

Trimming is cheaper still. Cutting out the half second in which a hand warps costs nothing. Give the agent a trim tool, and have it fix a shared clip from the cheapest option to the most expensive: trim first, then reword the change so an edit can make it, and remake only as a last resort. Keep every version of every asset, so a remake that turns out worse can be undone.

**If you're building one**

- Record the exact inputs of every image and clip, and find stale assets by comparing those records with the current film.
- Have a fast model choose between keeping, editing and remaking each stale asset, from a clear description of what edits can and cannot change.
- Write edit instructions in visual terms, never in tags.
- Prefer a trim to an edit and an edit to a remake, remake only the smallest run of shots, and keep every version.

## 4. Review Loop

A video agent cannot fix problems it never sees, and even a multimodal agent rarely watches the film it is making. The agent writes the script long before any images or clips exist, it does not check the results on its own, and many language models still cannot watch video with sound (in Doki, Gemini watches the clips for the agent). Yet almost every problem in this post shows up only in the images and videos. The harness therefore needs a review loop that checks the output automatically at fixed points and sends its findings back to the agent as tool results.

### Reviews the harness runs

An agent will not inspect its own work unprompted. I gave Doki's agent a tool that let a vision model watch any shot and answer questions about it, and across sixteen writing runs, the agent used it zero times. So the reviews run in the harness, the code around the agent that runs its tools:

<ReviewFigure />

In storyboard tests, films made with these reviews won most blind comparisons against films made without them, with about a fifth fewer continuity breaks.

### The first-time viewer

The most useful check is what I call the first-time viewer. A separate model watches the finished film without seeing the script or the user's request, and says what it understood. The regular film review has read the script, so it fills in story details that the screen leaves out. The first-time viewer has only the video and its sound, so wherever its account differs from the script, the film is failing to tell the story.

<Prompt from="Doki's first-time viewer">
  Say what you understood, in plain words: [...] What you couldn't follow: who
  someone is or is to someone else, why something happens, where things are,
  what something means, what comes out of nowhere, what you expected that never
  came - each with its shot.
</Prompt>

### What makes reviews work

- **Watch clips, not frames.** Findings from watching whole clips with sound held up almost every time, while findings from three still frames per clip held up only about two times in three. Only whole clips revealed a bicycle rolling backward, a hand that never lets go of a cup, or a voice that changes between shots.
- **Check the output, not the script.** Most continuity errors happen during generation: a cut inside a clip forgets where someone was standing, or a prop changes shape. A checker that reads only the script cannot see these. In my tests, a text-only continuity checker flagged many issues in the scripts and changed nothing in the films.
- **Fixes must fit the film.** Left alone, the agent responds to story feedback by adding more events to the script, and clips with too much happening break more often. Every review should say that a fix "has to fit in the shots the film has [...] and never add a shot, a part or a cut."
- **Cap the loop.** Review each shot at most three times per request. Without a cap, the agent can keep remaking a shot to satisfy its own critiques.
- **Evaluate the agent on films.** The same holds when you test a change to the agent itself. Judge finished films, watched blind, rather than the prompts the agent wrote. A prompt change can look much better to a judge reading the prompts, yet make no difference to the clips those prompts produce.

**If you're building one**

- Run reviews automatically in the harness, and return their findings in the tool results.
- Review whole clips with sound and the assembled film, and add a first-time viewer that has not read the script.
- Require fixes to fit the existing shots, and cap the number of reviews per shot.
- Evaluate changes to the agent on finished films, not on its prompts.

## Describe, Don't Prescribe

One principle connects all four components: describe to the agent how the models behave and what the film needs, instead of prescribing rules, examples or rules of thumb. When a prompt explains how the system works, the agent can reason about situations the prompt never anticipated. When a prompt gives a rule, the agent follows it literally, even where it no longer applies.

Prescriptions fail in predictable ways:

- **Rules are applied blindly.** A rule to "fade in and out of the whole video" also put fades around a single tense dialogue scene.
- **Examples are copied.** One sample scene that opened on a wide shot and cut to a close-up made the agent open twice as many scenes that way.
- **Numbers become targets.** Told that a scene becomes "one clip, of up to 15s", the agent cut its scenes to fit, even scenes set in one place.
- **Categories invite judgment calls.** Asked to define "characters and key places or objects", the agent decided that a coin and a scarf were not key.

The fixes in this post describe how the system behaves instead. The agent prompt explains that the models redraw anything without a definition from scratch every time, however small or plain it is. The video prompt writer is told that stopping before a cut makes the film halt there. It is also told when a stop is right: at the end of a scene, or during a deliberate pause. The update judge is told what an edit can and cannot change, and it decides each case itself.

There is one exception. Facts alone failed when a habit's payoff was invisible to the agent. Told only what a reference image does and what it costs, the agent created almost none, because the benefit shows up only in images and videos it never sees while it writes. A habit like this has to be stated outright, or enforced in code. A comment at the top of Doki's agent prompt records why:

<Prompt from="Doki's agent prompt, its opening comment">
  [...] the habits whose payoff shows only in images and videos it never sees:
  the three that keep a film consistent (a scene in one paragraph, reference
  shots, an ALL for the shared look) [...] Told only what those do, the agent
  left them out: its films were rows of long single takes.
</Prompt>

**If you're building one**

- Tell the agent what exists, how the models behave and what each choice costs, instead of telling it what to do.
- Leave out rules, examples, numbers and categories that the agent would have to interpret, because it follows each one literally.
- State outright the habits whose payoff the agent cannot see, or enforce them in code.

## Looking ahead

None of these ideas is tied to Doki. Whether the agent is a chat agent calling a video API, a node-based canvas or a timeline editor, making a long film means coordinating dozens of separate generations. So it needs a definition system, a shot planner, incremental editing and a review loop. Video models will take over parts of this as clips grow longer, reference limits rise and editing improves. Even so, a film will still be made of many separate generations, and the agent will still not watch the result unless the harness makes it.

I am still working through many of these problems. If you are building a video agent too, I would like to hear what has worked for you. You can try Doki with your own API keys at [doki.mov](https://doki.mov), and our paper with [Mira Dontcheva](https://research.adobe.com/person/mira-dontcheva) and [Dingzeyu Li](https://dingzeyu.li/) appears [at UIST 2026](https://dl.acm.org/doi/10.1145/3830398.3830715).
