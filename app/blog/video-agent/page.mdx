# Designing a Video Agent That Can Actually Make a Long Film

<PostMeta post="video-agent" date="November 2026" />

Video models are now genuinely good. They create stunning, high-quality visuals, and the newest ones, such as [Seedance 2.5](https://seed.bytedance.com/en/blog/one-take-creation-flexible-referencing-introducing-seedance-2-5) and [MiniMax H3](https://minimax.io/blog/minimax-h3), can generate several shots, with cuts between them, in a single clip.

However, making a whole film remains hard, even for a one-minute video. Most people still work shot by shot. They generate images and clips on an infinite canvas such as [Firefly Boards](https://www.adobe.com/products/firefly/features/boards.html), [FLORA](https://www.florafauna.ai/), [TapNow](https://www.tapnow.ai/) or [LibTV](https://www.liblib.tv/), or in research tools such as [VideOrigami](https://arxiv.org/abs/2503.04103) that add a script and a scene planner. Then they assemble the takes that work. Some people hand this workflow to a coding agent such as [Claude Code](https://www.anthropic.com/product/claude-code), or to the built-in agents in these tools.

The result tends to play like a **slideshow**.

If you try to make a one-minute film with Claude Code and a video model, you will quickly see the problem: the film doesn't look continuous. Each shot looks fine on its own, but the motion stops and restarts at every cut, nothing plans the pacing of the shots, and the same character looks different from shot to shot.

Individual clip quality is no longer the bottleneck. Current video agents were not designed for long videos, so their harnesses (the code that runs the agent and its tools) leave the problems specific to film unsolved: planning and pacing the shots of a scene, keeping people, places and looks consistent, keeping motion continuous across cuts, and making the story flow from one scene to the next.

I have been working on these problems in [Doki Agent](https://doki.mov) (Doki's interface is also super interesting, and I will cover it in a separate post). This post describes the four components that did most of the work to turn many clips into one coherent film, and the principle behind all of them. I believe any video agent needs these, regardless of how it is built:

1. **Definition System**: how the agent tracks things that must look the same, and how it sets up each generation to keep them consistent.
2. **Shot Planning**: how the agent splits a scene into video generations for the best continuity.
3. **Incremental Editing**: how the agent applies a change to the film without regenerating everything from scratch.
4. **Review Loop**: how the agent checks what it made and improves the film on its own.
5. **Describe, Don't Prescribe**: how to instruct the agent, by describing how the models behave and what the film needs instead of prescribing rules.

The examples come from Doki, with its actual prompts and algorithms.

## 1. Definition System

A long film must keep its people, places, objects and visual styles consistent across dozens of generations, but image and video models remember nothing from one generation to the next. Each generation sees only its own prompt and a few reference images, so anything described only in text is redrawn every time. That is why the same character, place or object looks different from shot to shot. A video agent therefore needs a **definition system**. Everything the film reuses is defined once, with a description and a reference image, and every shot references that definition instead of describing the item again.

### Definitions

A definition has four parts: a type (character, place, object or look), a name that the script can reference (with an @ in Doki), a text description, and a reference image generated from that description. Here are two examples from a short film made in Doki:

<Definitions />

Every shot that references <T>@Camera</T> is generated with its reference image, so the camera looks the same in every shot. The image carries most of the consistency, and the description is what the image is generated from.

### What gets a definition

Anything that appears more than once and must look the same needs a definition, however small or plain. Without one, a coin, a takeout bag or a scarf is redrawn from its words in every shot and comes out different each time. So do not leave it to the agent to decide which items are important enough. Tell it how the models behave instead:

<Prompt from="Doki's agent prompt">
  Without one, they get only its text, and each picture draws it anew - each
  shot's image, and each later cut, which has no image of its own: the same
  words come out as a different face, outfit, place or object each time, however
  small or plain it is. [...] So whatever is seen more than once and should look
  the same each time - someone, a place, a vehicle, a prop - gets a definition
  with a reference shot.
</Prompt>

A reference image also locks in everything it shows. If a shop's reference shows its exterior, every shot that uses it is pulled toward an exterior view, even a shot set inside. So an interior, a costume from another period, or what a character transforms into each needs a definition of its own.

### Scoping

Different definitions apply to different parts of the film. The visual style should hold in every shot, the weather of one sequence only in that sequence, and a camera move only in one shot. So a definition system needs scopes, much like style rules in CSS:

- **Film.** A film-wide definition applies to every shot without being referenced. It holds what the whole film shares, such as its look, lighting and mood.
- **Part of the film.** A definition attached to an act or a sequence applies to every shot inside that part, and to nothing outside it.
- **Shot.** A definition referenced in a shot applies to that shot alone.

Two rules keep scopes predictable. A definition applies only where it is referenced or scoped, wherever it is written. And scopes add up instead of overriding one another: a shot with its own style still receives the film-wide style, so the local choice refines the shared look instead of replacing it.

### Resolving a shot

Definitions can be nested and can depend on other definitions. A photo of a character on a train platform, for example, depends on both the character and the platform. The references form a dependency graph, and resolving a shot means walking that graph. In the shot below, a close-up of three photos on a shop counter, each photo is a definition that references others:

<ResolveFigure />

The agent walks the graph depth-first, from the shot's own references and every film-wide or part-level definition in scope, and outputs each definition after the ones it depends on:

```ts
const resolve = (def: Definition) => {
  if (seen.has(def)) return // each once, so cycles stop
  seen.add(def)
  referencesIn(def.description).forEach(resolve)
  ordered.push(def) // after everything it uses
}
;[...shot.references, ...inScope(shot)].forEach(resolve)
```

The prompt lists the definitions in this order, so by the time the model reads that a photo shows a character on a train, it already knows who that character is. Keep the graph, too. Read in reverse, it shows what a change affects: if a character changes, every shot that uses them, directly or through a photo, is out of date (Section 3).

### Choosing the reference images

A shot can use more definitions than a model accepts reference images. So the agent must choose which reference images to include to make the most accurate image or video. In our experiments, two rules worked well:

- **The scene so far.** When generating a new image, include the images of the scene's earlier shots, so the place, lighting and people stay the same. This was the largest consistency improvement I measured: it cut continuity errors by more than half.
- **What the first frame does not show.** A video starts from its first frame, which already shows everyone on screen. Spend the remaining slots on what that frame leaves out, such as a person about to enter or the place a cut leads to.

The prompt should also tell the model what to take from each reference image, or the model may copy the wrong thing. For example, if an image is there only for its style, the model may also copy what the image shows into the shot. So when we write the prompt, we must say clearly which part of each reference image to use:

<Prompt from="Doki's image prompt writer">
  An image that is "the overall style" [...] gives only that quality ("in the
  art style of image 3"). Never put its content in the shot.
</Prompt>

### Text overrides images

Image and video models follow the prompt's words more closely than its reference images. If a character's reference shows red boots but the prompt says yellow boots, the model draws yellow boots. Models also sometimes ignore the reference and draw from the words alone, so a character described only by her green cardigan can come out as a different woman in that cardigan. So the prompt should never add looks to anything that has a definition, and it should describe each character by who they are (age, face, hair and build) before what they wear.

Cuts inside a video have the same problem. When a video model generates several shots in one clip (Section 2), only the first shot has an image to start from, so the shots after a cut are drawn from the words alone and drift from the film's look. In our test, black-and-white scenes turned to color after the cut in 3 of 6 clips, and in none once the prompt repeated the look at every cut:

<Prompt from="Doki's video prompt writer">
  The video model draws each later shot afresh and drifts from the film's look
  unless told it, so open each shot after the first with the look in a few words
  [...] ("cuts to a close-up, in the same high-contrast black and white: …").
</Prompt>

<Takeaways>

- Give everything that appears more than once and should look the same a definition with a reference image, and do not let the agent judge what is important enough.
- Scope definitions to the film, a part of it or a single shot, and let scopes add up rather than override.
- Resolve definitions depth-first, list them in dependency order, and keep the graph to trace changes in reverse.
- Spend the reference slots on the scene so far and on what the first frame leaves out, and say which part of each image to use.
- Never add looks in text to something that has a definition, describe each character by who they are before their clothes, and repeat the look at every cut.

</Takeaways>

## 2. Shot Planning

A film is a series of **shots**. Each shot is one continuous view, and a **cut** switches to the next one. A run of shots in one place and time is a **scene**. A video agent usually plans each scene as a **shot list**, with the words for every shot and a **keyframe**, the storyboard image the shot should open on. Then it calls the video model, and each call, or **generation**, returns one clip.

Most video agents make films that look like a slideshow, because they generate one clip per shot and stitch the clips together. In Doki Agent, we introduce a shot planner instead. It decides which shots to generate together in one clip, and where to split a long scene into several clips.

### Which shots go together?

When every shot is its own clip, each one starts over from its keyframe, so motion and sound restart at every cut. Newer video models can generate several shots in one go and cut between them, and inside one generation the people, the light, the motion and the sound carry across each cut. In my tests, this beat generating shots one by one in most comparisons, with about a third fewer continuity breaks.

But every model has limits. Some make one shot per generation. MiniMax H3 makes up to 15 seconds of shots, and Seedance 2.5 up to 30. A longer scene needs several generations, so the agent has to decide which shots go together.

Take a scene of four shots. At night, a woman folds a paper boat (shot 1) and sets it on the windowsill (shot 2). The next morning, she runs out (shot 3) and lets it go on a puddle (shot 4). The four shots run 19 seconds, too long for one MiniMax generation. The naive answer is to pack each generation full: shots 1 to 3 fill the first 15 seconds, and shot 4 gets a generation of its own.

The packed film doesn't look continuous. The first generation carries the night on into the morning, so the morning opens in last night's kitchen. And the split falls in the middle of her run, so she is running at the end of one clip and suddenly crouching at the start of the next. Another strategy fixes both: split the scene where it jumps to the next morning, so shots 1 and 2 make one generation and shots 3 and 4 the next. Then the new generation opens on the morning's keyframe, and her run and crouch stay in one generation.

<ResultFigure />

So this is a planning problem: keep shots in one generation where the story flows, and start a new generation where it jumps.

### How the planner works

The planner uses a vision-language model (VLM) and a dynamic programming algorithm, each for what it does well. The VLM (Gemini, in Doki) looks at the keyframes and judges what each cut and shot needs, which takes taste. Dynamic programming then picks the grouping, an optimization with hard limits that language models are bad at. On 11 hard scenes, plans made this way passed 32 of 32 editing checks, while plans that Gemini wrote directly passed 79 to 85%. It works in three steps.

**1. A VLM reads the shot list.** It reads each shot's words and keyframe, and rates two needs from 0 to 3: how much each cut needs the shots on both sides to flow together, and how much each shot needs a fresh start on its own keyframe.

<Rubric />

The ratings describe the film, not the video model, so one reading works for any model. The keyframes matter too: rated from the words alone, the same scenes passed only 28 of the 32 checks.

**2. Each video model gets its own prices.** How much a split cut or a missed fresh start hurts the film depends on the video model, so each model needs its own price for each rating. To measure them, I generated the same test scenes two ways, in as few generations as possible and with one generation per shot. A judge model then scored each cut and shot that came out differently, from 1 to 10, and the difference in score is the price. For MiniMax H3, splitting a cut rated 2 or 3 cost about 1.2 points, and so did a shot rated 2 or 3 that came mid-generation instead of getting a fresh start. Ratings of 0 and 1 cost almost nothing. A model that has not been measured simply gets the fewest generations that fit.

**3. Dynamic programming finds the grouping that loses least.** A scene of n shots can be grouped 2<sup>n−1</sup> ways, and the algorithm finds the best one that fits without listing them all. Let best[j] be the least a plan for the first j shots can lose. The last generation of that plan covers shots i+1 through j, so:

In words, each generation adds three costs to the plan. S is the cost of the cut where the generation starts, because that cut now splits the shots on both sides. F is the cost of each shot after its first, because those shots don't get a fresh start on their keyframes. The last term is what the generation costs in dollars, at half a point a dollar, so money counts a little too. The boat scene can be grouped eight ways, and seven of them fit in MiniMax's 15-second generations. ### What the plan does

For MiniMax, the planner picks the split of Fig. 2: shots 1 and 2 make the night, and shots 3 and 4 the morning. It pays for this, because shot 4 now comes mid-generation and only lands near its keyframe. The planner judged that cheaper than breaking her run.

A longer scene shows the same logic at scale. It has ten shots in three parts: a morning in the kitchen, a long stretch at the river, and an evening downstream. Packing makes both mistakes again. The plan starts fresh at both jumps in time, and splits the river part where the boat drifts away from her. Seedance, with 30 seconds per generation, needs only two:

<RiverFigure />

The plan does not always win yet. On two other test scenes, packing did better. In one of them, a planned generation opened on a close-up and had to invent the room around it, a cost the prices do not include yet.

### Writing each generation

Once the plan is set, each generation needs two prompts: an image prompt for the keyframe it opens on, and a video prompt for its motion. Both must give the model something to play and keep it moving.

**Open on the first instant.** Image models draw any action the prompt names as already done. "She walks to the porch, crouches and watches the kitten" comes out with her already crouched, and the clip has nothing left to play. So Doki's prompt writer first names the opening instant on its own line (`OPENING: she reaches the porch steps`), then describes the keyframe as a still photograph of it:

<Prompt from="Doki's image prompt writer">
  The image model draws whatever the prompt names as done: an action's verb,
  even with "starting to" or "about to", comes out finished ("starting to sit"
  comes out seated) [...] So write the prompt as a still photograph of that
  instant, in states rather than actions: where each person is, where their
  hands, gaze and weight are, and where each object is.
</Prompt>

**Keep moving through the cut.** Video models tend to slow to a stop at the end of a clip, so the video prompt writer is told what that does to the film:

<Prompt from="Doki's video prompt writer">
  A clip that slows to a stop before its cut makes the film halt there, and when
  every clip does, the film plays like a row of stills. So unless NEXT SHOT is
  none, keep the action and the camera moving through the last second [...]
</Prompt>

**Translate the plan for each model.** Keep the plan independent of the model, as a list of shots with their timings, and write it out in each model's own syntax. MiniMax, for example, ignores timed spans such as `[2-4s] cut to …` and often cuts at about two seconds regardless. Written in its own shot-list syntax, as in the plan's morning generation, it cuts within a few hundredths of a second of each timestamp:

<Takeaways>

- Generate a scene's shots together whenever the model supports it.
- Let a VLM rate what each cut and shot needs, price each rating per video model, and let dynamic programming choose the grouping.
- Write each keyframe as a still photograph of the opening instant, and keep each generation moving through its cuts.
- Keep the plan independent of the model, and keep generation limits out of the script.

</Takeaways>

## 3. Incremental Editing

A long film is never right on the first try. A character's hair changes, a planet should be frozen, a line of dialogue is added. The obvious response is to regenerate every shot a change touches, but regeneration is a gamble: in my logs, it fixed the flagged problem only about half the time. It also throws away what was already right, such as the camera angle, the faces and the take the user approved.

A video agent should instead treat the film like a software build. It tracks exactly which assets are out of date and rebuilds as little as possible, editing wherever it can. Current image and video models can edit: given an image or a clip and an instruction, they change what was asked and keep the rest.

### Staleness is a diff

For every image and clip, record the inputs that made it: the shot's text, the resolved definitions, the versions of the reference images, and for a video, its keyframe, its timing and the generation it shares with other shots. An asset is stale when its record differs from the current film, and the difference is the reason. Say the user decides the film's Mars should be frozen instead of red. Every shot of Mars now differs from its record, with the reason "<T>@Mars</T> changed". Because definitions are resolved through the graph from Section 1, the change also reaches every shot that uses Mars indirectly.

### Keep, edit or remake

For each stale image or clip, a fast model compares the recorded inputs with the shot's new state and chooses to keep the asset, edit it or remake it. For the frozen Mars, a remake would redraw the whole shot, while an edit freezes only the ground:

<UpdateFigure />

Most of the judge's prompt describes what an edit can and cannot change:

<Prompt from="Doki's update judge">
  An edit does a change that sits in the picture: a color, clothes, hair or
  makeup, an object added, removed or swapped, the state an object is in, an
  expression, the light, the weather or the time of day, written text, the
  style. [...] It can't move the camera or change the framing, move people,
  change what they do or how they move, or set the shot somewhere else; in a
  video it can't change what is said, the voices or the timing.
</Prompt>

The edit model sees only the picture, not the script, so the judge writes its instruction in visual terms ("the woman in the red coat") rather than definition names. On 62 labeled cases, Doki's judge chose correctly 61 times. Rules that must always hold stay in code: a failed edit falls back to a remake, and a photo the user uploaded is never overwritten. Every video edit goes to a model that keeps the original take, whichever model made the clip. Doki uses [Gemini Omni](https://ai.google.dev/gemini-api/docs/omni), which changes what was asked and keeps the motion frame for frame.

### Remake the smallest run

When several shots share one generation, changing one of them should not regenerate the whole scene. An edit can run on that shot's segment alone. A remake regenerates only the run of neighboring shots that need new video, at the cost of a new split there. Trimming is cheaper still: cutting out the half second in which a hand warps costs nothing. So give the agent a trim tool and have it fix a shot in order of cost, trimming first, then editing, and remaking only as a last resort. Keep every version, so a remake that turns out worse can be undone.

<Takeaways>

- Record the exact inputs of every image and clip, and find stale assets by comparing those records with the current film.
- Have a fast model choose between keeping, editing and remaking each stale asset, from a clear description of what edits can and cannot change.
- Write edit instructions in visual terms, never in tags.
- Prefer a trim to an edit and an edit to a remake, remake only the smallest run of shots, and keep every version.

</Takeaways>

## 4. Review Loop

A video agent cannot fix problems it never sees, and even a multimodal agent rarely watches the film it is making. It writes the script long before any image or clip exists, it does not check the results on its own, and many language models still cannot watch video with sound (in Doki, Gemini watches the clips for the agent). Yet almost every problem in this post shows up only on screen. So the harness needs a review loop that checks the output automatically at fixed points and sends its findings back to the agent as tool results.

### Reviews the harness runs

An agent will not inspect its own work unprompted. I gave Doki's agent a tool that let a vision model watch any shot and answer questions about it, and in sixteen writing runs the agent used it zero times. So the reviews run in the harness, each set off by what the agent just did. Doki runs four: on the script, on each new image or video, on the whole storyboard, and on the finished film. Each review's findings come back in the result of the tool that set it off:

<ReviewFigure />

In tests on storyboards, films made with these reviews won most blind comparisons against films made without them, with about a fifth fewer continuity breaks.

### The first-time viewer

The most useful check is what I call the first-time viewer. A separate model watches the finished film without seeing the script or the user's request, and says what it understood. The film review has read the script, so it fills in story details that the screen leaves out. The first-time viewer has only the video and its sound, so wherever its account differs from the script, the film is failing to tell the story.

<Prompt from="Doki's first-time viewer">
  Say what you understood, in plain words: [...] What you couldn't follow: who
  someone is or is to someone else, why something happens, where things are,
  what something means, what comes out of nowhere, what you expected that never
  came - each with its shot.
</Prompt>

### What makes reviews work

- **Watch clips, not frames.** Findings from watching whole clips with sound held up almost every time, while findings from three still frames per clip held up only about two times in three. Only whole clips revealed a bicycle rolling backward, a hand that never lets go of a cup, or a voice that changes between shots.
- **Check the output, not the script.** Most continuity errors happen during generation, such as a cut that forgets where someone was standing or a prop that changes shape, so a checker that reads only the script cannot see them. In my tests, a text-only continuity checker flagged many issues in the scripts and changed nothing in the films.
- **Fixes must fit the film.** Left alone, the agent answers story feedback by adding events to the script, and clips with too much happening break more often. Every review should say that a fix "has to fit in the shots the film has [...] and never add a shot, a part or a cut."
- **Cap the loop.** Review each shot at most three times per request. Without a cap, the agent can keep remaking a shot to satisfy its own critiques.
- **Evaluate the agent on films.** The same holds when you test a change to the agent itself: judge finished films, watched blind, not the prompts the agent wrote. A prompt change can look much better on paper and make no difference to the clips.

<Takeaways>

- Run reviews automatically in the harness, and return their findings in the tool results.
- Review whole clips with sound and the assembled film, and add a first-time viewer that has not read the script.
- Require fixes to fit the existing shots, and cap the number of reviews per shot.
- Evaluate changes to the agent on finished films, not on its prompts.

</Takeaways>

## 5. Describe, Don't Prescribe

One principle connects all four components: describe to the agent how the models behave and what the film needs, instead of prescribing rules, examples or rules of thumb. When a prompt explains how the system works, the agent can reason about situations the prompt never anticipated. When a prompt gives a rule, the agent follows it literally, even where it no longer applies.

Prescriptions fail in predictable ways:

- **Rules are applied blindly.** A rule to "fade in and out of the whole video" also put fades around a single tense dialogue scene.
- **Examples are copied.** One sample scene that opened on a wide shot and cut to a close-up made the agent open twice as many scenes that way.
- **Numbers become targets.** Told that a scene becomes "one clip, of up to 15s", the agent cut its scenes to fit, even scenes set in one place.
- **Categories invite judgment calls.** Asked to define "characters and key places or objects", the agent decided that a coin and a scarf were not key.

Each fix in this post is a description instead. The agent prompt explains that the models redraw anything without a definition. The video prompt writer learns what a stop before a cut does to the film, and when a stop is right. The update judge learns what an edit can and cannot change. In each case, the agent decides for itself.

There is one exception. Facts alone fail when the payoff of a habit is invisible to the agent. Told only what a reference image does and what it costs, the agent created almost none, because the benefit shows up only in images and videos it never sees while it writes. A habit like this has to be stated outright, or enforced in code. A comment at the top of Doki's agent prompt records why:

<Prompt from="Doki's agent prompt, its opening comment">
  [...] the habits whose payoff shows only in images and videos it never sees:
  the three that keep a film consistent (a scene in one paragraph, reference
  shots, an ALL for the shared look) [...] Told only what those do, the agent
  left them out: its films were rows of long single takes.
</Prompt>

<Takeaways>

- Tell the agent what exists, how the models behave and what each choice costs, instead of telling it what to do.
- Leave out rules, examples, numbers and categories that the agent would have to interpret, because it follows each one literally.
- State outright the habits whose payoff the agent cannot see, or enforce them in code.

</Takeaways>

## Looking ahead

None of these ideas is tied to Doki. Whether the agent is a chat agent calling a video API, a node-based canvas or a timeline editor, making a long film means coordinating dozens of separate generations, so it needs a definition system, a shot planner, incremental editing and a review loop. Video models will take over parts of this as clips grow longer, reference limits rise and editing improves. Even so, a film will still be made of many separate generations, and the agent will still not watch the result unless the harness makes it.

I am still working through many of these problems. If you are building a video agent too, I would like to hear what has worked for you. You can try Doki with your own API keys at [doki.mov](https://doki.mov), and our paper with [Mira Dontcheva](https://research.adobe.com/person/mira-dontcheva) and [Dingzeyu Li](https://dingzeyu.li/) appears [at UIST 2026](https://dl.acm.org/doi/10.1145/3830398.3830715).
